## 2. 만들 것 (합친 안)

### 2.1 골격: Claude 안의 구조를 따름
1. **잇는 조건.** 줍기 다시 잇기는 인벤토리 묶음의 `ExtraUniqueID`가 **(바닥 참조 FormID, 스탬프)와 정확히 같고, 젬 종류도 같을 때만** 합니다(결정 59 "참조와 번호를 함께 본다"). Claude 안의 `WorldStampLink::FindWorldLinkTarget`과 같은 규칙입니다.
2. **장부 커밋.** 장부는 "아직 기대한 바닥 키일 때만" 바꿉니다(Claude 안 `CommitRelink`). 커밋에 실패하면 엔진 묶음을 건드리지 않습니다.
3. **잠금 순서.** 후보 수집(젬 잠금) → 묶음 탐색과 번호 할당(잠금 밖) → 키 이동(젬 잠금) → 묶음 고쳐 쓰기(잠금 밖) 순서로 합니다. 번호 할당기는 수집 콜백에서 젬 잠금을 잡으므로, 젬 잠금을 쥔 채 할당하면 교착이 납니다.
4. **실물 재확인.** 묶음을 고쳐 쓰기 직전에 그 묶음이 **아직 (바닥 참조, 스탬프)를 달고 있는지** 다시 확인합니다. 두 안 모두 빠뜨린 것입니다(Codex 지적 A5).
5. **동등 후보.** 정확히 맞는 묶음이 둘 이상이면 어느 것도 잇지 않고 경고 로그만 남깁니다. 한 묶음의 개수(`GetCount()`)가 1보다 크면 그 묶음도 보류하고 로그를 남깁니다. 우리 젬은 스탬프마다 하나라서 정상 경로에서는 일어나지 않아야 합니다.
6. **줍기 싱크.** `TESContainerChangedEvent` 싱크는 다음 조건이 모두 맞을 때만 반응합니다: `oldContainer==0 && newContainer!=0`, 스탬프가 젬 대역(`0x7F00..0xBFFF`) 안, 베이스가 우리 젬, `itemCount > 0`. 싱크 안에서는 메모리만 대조하고, 다시 잇기는 주 갱신 큐에 예약합니다(결정 118·119·123).
7. **보완 경로.** 줍기 예약이 실행되지 못한 경우(예약 전 저장, 로드 세대 폐기)에 대비해, 로드 직후 초기화와 패널 데이터를 만들기 직전에 플레이어 인벤토리를 다시 훑습니다. 두 안 모두 이렇게 했습니다. 단 패널 쪽 호출은 거래 잠금 밖에서 합니다. 그 호출 자리에 "g_txMutex 미보유" 계약 주석을 남깁니다.

### 2.2 Neon 안에서 가져올 것
1. **스탬프 선기록.** 버리는 이벤트 안에서 스탬프를 할당한 즉시 장부 키에 적습니다(`it->key.uniqueId = stampUid`). 그래야 `(참조, 0)` 대기 상태가 없어집니다. `ItemTracker`와 같은 방식입니다.
2. **다시 버린 경우.** 스탬프를 남기는 조건을 `newBase != 0 && newUid == 0`으로 바꿉니다(두 안 공통). 줍고 나서 다시 잇기 전에 또 버린 젬도 새 스탬프를 받아야 합니다.
3. **보완 스탬프 실행 전 재검증.** 주 갱신에서 보완 스탬프를 남기기 전에 두 가지를 다시 확인합니다. 하나는 그 항목이 아직 그 참조에 있는 바닥 항목인지(Neon 안 `MatchesWorldEntry`)입니다. 다른 하나는 바닥 참조의 실제 베이스가 그 항목의 젬 종류와 같은지입니다. 이미 다른 스탬프를 단 참조는 덮어쓰지 않습니다(Codex 지적 A2·B2).
4. **저장 직렬화.** 다시 잇기 한 번(키 이동 + 묶음 고쳐 쓰기)을 `SaveLoad::RunSerializedTransaction`으로 감싸, 젬 장착 거래(결정 137 (마))와 같은 관례를 따릅니다. 이때 위 3번(잠금 순서)은 그대로 지킵니다: 거래 잠금 → 젬 잠금 순서이고, 젬 잠금 안에서는 엔진을 부르지 않습니다. 저장 콜백이 주 갱신과 같은 스레드에서 도는지는 미확인입니다. 그러니 이 직렬화가 실제로 효과가 있는지도 "미확인"으로 적습니다.
5. **시험 설계.** 상태 전이를 엔진과 상관없는 코드로 떼어 시험하는 발상은 가져옵니다. 다만 저장소 전체를 교체하지 말고 **판단 함수 수준으로 좁혀서** 씁니다.

### 2.3 넣지 말 것 (Neon 안에 있던 것)
- **`(소유자, 스탬프)` 2순위 대조.** 정확한 바닥 키가 없을 때 소유자 키 묶음 하나를 받아들이는 분기입니다. 관찰된 적 없는 엔진 동작을 가정했고, 다른 젬에 데이터를 잘못 붙일 수 있습니다(Codex 지적 B1, 높음).
- **고유 ID 0 줍기 폴백.** 프로토타입 5 README 419·707행의 관찰상, 고유 ID 칸이 0인 줍기는 스탬프가 없다는 뜻이라 이 폴백은 성공할 수 없습니다.
- **일반 젬 수량 계산의 `max(1, GetCount())` 변경.** 과제와 무관합니다.
- **젬 추적 저장소 전체 교체.** 회귀 범위가 너무 넓습니다.
- **고유 ID 변경 싱크의 `objectID` 필터.** 필요하지만 과제 밖입니다. 검수 문서의 C-35로 따로 다룹니다.

### 2.4 시험 (제품 코드를 거칠 것)
흐름 시험이 제품 코드의 판단 함수와 장부 커밋을 실제로 부르게 하고, 손으로 흉내 낸 사본을 시험하지 않습니다. 최소한 아래를 넣습니다.

1. **음성 시험 (Codex 제안).** 젬 X는 바닥에 두고, 같은 종류의 젬 Y에 `(플레이어, X의 스탬프)`를 부여합니다. 그 상태에서 보완 경로(목록 조회나 패널 갱신 경로의 판단 함수)를 돌려 **X와 Y 모두 변하지 않는지** 확인합니다.
2. **저장 경계 시험 (Codex 제안).** 정상적으로 주운 X의 다시 잇기를 저장 경계에서 끊었다가 복원합니다. 그 뒤 **같은 `instanceId`가 목록 조건에 정확히 한 번 나오고**, 실제 `GemTransaction`으로 재장착되며, 중첩 보조 젬까지 보존되는지 확인합니다. 재장착 부분은 Neon 안의 시험에서 가져옵니다.
3. **기타 경우.** 다시 잇기 전에 또 버린 경우, 같은 종류 여러 개, 바닥 참조 FormID 재사용, 동등 후보가 둘인 경우(보류되는지), 커밋 실패 시 엔진 묶음을 건드리지 않는지.
4. **기능 제거 점검.** 시험이 기능을 빼면 실패하는지 직접 확인합니다. 예를 들어 묶음 고쳐 쓰기를 빼도 통과하면 시험이 잘못된 것입니다.

  - 동등 후보 보류
  - 저장 직렬화
- **보고.** 검수 문서의 C-1 항목에 `→ 처리: …(날짜)`를 덧붙이고, 다음을 적습니다.
  - 바꾼 파일
  - 직접 돌린 검증과 그 결과
  - 미확인 목록
- **미확인 목록에 반드시 넣을 것.** 실행으로 확인하지 않았다면 다음 항목을 모두 넣습니다.
  - 젬 MISC에서도 줍기 이벤트가 프로토타입 5(검·투구·주괴)와 같은 모양으로 오는지
  - 주 갱신에서 `ExtraUniqueID`를 고쳐 쓰는 방식(결정 123 기록상 미확인)
  - 다시 잇기 전에 묶음을 옮기거나 버릴 때 엔진이 옛 키로 이벤트를 보내는지

  - 엔진의 순차 UID가 우리 대역과 겹치지 않는지
- **보고서 표현.** 확인하지 않은 것을 "처리함", "보장"으로 적지 않습니다. 이번 비교에서 감점된 부분입니다.
- **게임 안 확인 순서(사용자 허락 뒤).** 다음 4가지를 한 번씩 봅니다.
  1. 버리고 바로 줍기
  2. 버리고 저장·불러오기 뒤 줍기
  3. 줍고 다시 잇기 전에 또 버리기
  4. 동료가 주운 것을 건네받기
