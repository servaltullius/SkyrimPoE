# 7단계 P0 공통 계약

- **상태**: 2판(2026-11-24, Claude 작성). 1판을 Codex 교차 검토(gpt-6.2-astra, 판정 "수정 후 재검토")로 고쳤습니다(10장). 2판은 재검토 전입니다. 결정 190(세이브), 191(공개 범위), 192(FormID)를 구현 규칙으로 옮긴 것입니다. 표시가 [제안]인 것은 사용자 확인 전입니다. 8장의 C-1~C-3은 결정 194~196으로 확정됐습니다(2026-11-24).
- **위치**: `docs/7단계-PoE2-전환-계획.md` 6장의 P0 산출물입니다. P1~P8의 모든 작업은 이 문서의 ID·팩·세이브·ESP 규칙을 따르고, 규칙을 바꾸면 이 문서를 먼저 고칩니다.
- **근거**: 2026-11-24 코드 조사와 Codex 재현(파일:행은 본문). 게임에서 실행으로 확인한 것은 없습니다.
- **보장의 한계**: 이 계약이 지키는 것은 같은 시점에 저장된 `.ess`·`.skse` 쌍입니다. 둘이 서로 다른 시점의 것이면(한쪽만 복사, 한쪽 분실) 복구할 수 없고, 알리고 보존 모드(4.6)로 둡니다.

## 1. 용어

| 용어 | 뜻 |
| --- | --- |
| 원본 키 | PoB 데이터의 키(젬 `grantedEffectId`, 트리 노드 번호, 어픽스 `ModId` 등). 판마다 뜻이 바뀔 수 있음 |
| 콘텐츠 ID | 우리가 세이브·팩·UI에서 콘텐츠(젬, 노드, 어픽스, 클래스 등)를 가리키는 ID. 한 번 정하면 뜻이 바뀌지 않음 |
| 엔진 참조 | 세이브에 든 FormID 중 콘텐츠가 아닌 것(아이템 소유자, 바닐라 베이스, 바닥 드랍·액터 참조). `ResolveFormID`로 로드 순서만 맞춤 |
| 콘텐츠 세대 | 게임 팩·ESP·세이브가 같은 데이터 기준인지 가리는 정수. PoE1 시절 0, PoE2 0.5 1, 1.0 2 |
| 빌드 ID | 한 번의 패키징에서 함께 만든 팩·`tree-data.js`·ESP를 묶는 값(같은 세대 안의 다른 빌드를 가림) |
| 대응표 | 세대 N → N+1에서 옛 콘텐츠 ID의 처리(유지·이름 변경·환불·폐기)를 적은 표 |

### 2.2 7단계 규칙

1. **세이브의 콘텐츠 자리에는 콘텐츠 ID만 씁니다.** 원본 키는 게임 팩 안에서 콘텐츠 ID 옆에 `source`(판, 파일, 키)로만 둡니다. 엔진 참조는 지금처럼 FormID로 두고 `ResolveFormID`를 씁니다.
2. **콘텐츠 ID의 모양**(C-3, 결정 196으로 확정)
   - 모양: `종류.이름` 문자열. 예: `gem.IceNova`, `sup.Brutality2`, `affix.IncreasedLife7`, `unique.Goldrim`, `cls.Witch`, `asc.Infernalist`.
   - 허용 문자: ASCII 영숫자, `.`, `_`. 길이는 64바이트 이하입니다(저장기는 256바이트에서 자름, `SaveAffixList.h:11-19`).
   - 중복: 팩을 만들 때 종류마다 중복이 없는지 검사합니다.
   - 이름은 처음 채택한 판의 원본 키에서 만들고, 원본 이름이 바뀌어도 그대로 둡니다.
3. **노드는 (세대, 번호) 쌍으로 식별합니다.** 세이브 크기 때문에 노드는 u32로 두고, TREE와 GEAR 레코드에 그 번호가 속한 세대를 함께 저장합니다. 번호는 그 세대의 노드 표 안에서만 뜻이 있습니다. 세대가 바뀌면 대응표로 옮깁니다(4.5).
4. **클래스의 권위 필드는 하나입니다.** 새 TREE에 `cls.*`를 저장하고 이것을 권위로 삼습니다. CORE의 `className`은 표시용 사본으로 두고 로드 때 TREE에서 다시 채웁니다. 트리 팩의 "정확히 7개" 검사를 없애고, UI는 정수 대신 클래스 ID를 받습니다.
5. **의미 지문**: 판 비교 도구는 같은 원본 키라도 다음 가운데 하나가 바뀌면 "의미 변경"으로 분류하고, 자동으로 같은 콘텐츠 ID에 잇지 않습니다.
   - 이름, 스탯 문장
   - 값의 순서·단위·범위
   - 연결, 태그, 행동 필드
   - 참조하는 추가 효과(예: Ice Nova는 본체 외 stat set 둘을 참조, `Gems.lua:9-12`)
   - 수치만 바뀐 것은 "수치 변경"입니다.
6. **세대 0 저장 키**: 이미 배포된 세대 0의 저장 키(젬 `gemId`, 화폐 `CurrencyKind`, 토큰의 티어·희귀도·부위군, 벨트 번호, 주얼 색, `CharmKind`, 지도 티어)는 FormID 장부의 `legacyKey`에 적습니다(5.1). 구판 물건을 반환할 때의 조회와 현행 기능을 허용하는 조회는 다른 표를 씁니다(폐기 젬은 반환되지만 장착되지 않게).

## 3. 팩 계약

1. **파일 이름에서 판을 뺍니다.** `packs/core.json`, `packs/tree.json`, `packs/items.json`, `packs/rules.json`(새로). 판은 파일 안 `meta`에만 둡니다. CTest와 작성기 시험의 옛 파일 이름(`tests/test_datapack.cpp:19`, `tools/compiler/test_tree_compiler.py:172` 등)도 함께 바꿉니다.
2. **모든 팩에 같은 모양의 `meta`를 둡니다.**
   ```json
   {
     "meta": {
       "schema": "skyrimpoe.items",
       "schemaVersion": 3,
       "game": "poe2",
       "gameVersion": "0.5",
       "pobVersion": "0.23.1",
       "contentGeneration": 1,
       "buildId": "<패키징 때 정한 값>",
       "extractorVersion": "1",
       "sourceSha256": { "Data/ModItem.lua": "<sha256>" },
       "pobManifestSha1": { "Data/ModItem.lua": "<PoB manifest.xml의 sha1>" }
     }
   }
   ```
   - `sourceSha256`은 로컬 입력 파일에서 직접 계산합니다.
   - `pobManifestSha1`은 PoB 배포의 `manifest.xml`(SHA-1)에서 옮긴 출처 기록입니다.
   - 데이터 파일과 함께, 공식이 든 계산 모듈(`Modules/Data.lua`, `CalcDefence.lua`, `CalcOffence.lua`, `CalcPerform.lua`)도 넣습니다.
3. **패키지 목록**: 패키징 때 `SKSE/Plugins/SkyrimPoE/manifest.json`을 만듭니다. 내용은 `buildId`, `contentGeneration`, 파일별 SHA-256(네 팩, `tree-data.js`, UI 파일, `SkyrimPoE.esp`)입니다.
4. **DLL 검사**: 지금은 `meta`를 아무도 읽지 않습니다. 아래를 모두 만족해야 정상 모드(4.6)로 켭니다.
   - DLL이 허용하는 `game`, 세대, 파일별 `schema`·`schemaVersion`이어야 합니다.
   - 네 팩의 `contentGeneration`과 `buildId`가 같아야 합니다.
   - 팩 파일 해시가 `manifest.json`과 같아야 합니다.
   - ESP 표시 GLOB(5.1 규칙 5)의 값이 세대와 같아야 합니다.
   - 디스크의 `SkyrimPoE.esp` 해시가 목록과 같아야 합니다. MO2 가상 파일 시스템에서 읽히는지는 P2에서 확인합니다.
   - 어긋나면 보존 모드로 두고, 이유를 로그와 화면 알림(`RE::DebugNotification`, 패널이 없어도 보임)으로 보입니다.
   - core 실패와 tree·items 실패의 경로(`main.cpp:182-215`)를 하나로 합칩니다.
5. **UI 검사**
   - 패키징 때 `tree-data.js`에 `meta`를 넣습니다.
   - DLL은 UI가 보낸 `buildId`·UI 프로토콜 판이 자기와 같을 때만 상태를 바꾸는 명령(노드 할당·환불, 제작, 장착, 지도)을 받습니다. 다르면 거부하고 알립니다. 지금 UI는 숫자 노드 ID와 화폐 번호를 보냅니다(`UiBridge.cpp:1639-1701`, `ui/gear.js:451-503`).
   - 읽기 전용 화면은 경고만 띄웁니다.
6. **패키징 검사**
   - CMake `package_mod`는 패키지 폴더를 먼저 비웁니다(지금은 재사용, `CMakeLists.txt:196-205`).
   - 최종 패키지에서 `manifest.json`과 실제 파일을 대조하고, 목록 밖 파일이 남으면 실패합니다. 지도 팩의 이중 대조(`CMakeLists.txt:186-200`)가 선례입니다.
   - `tree-data.js`는 패키지에 복사한 `tree.json`에서 만듭니다.
7. **배치**: `build.bat deploy`는 덧쓰기(`/e`)입니다. 배치 뒤 대상 폴더를 `manifest.json`과 대조하고, 목록 밖의 우리 파일(옛 `*_3_30.json` 등)을 지운 뒤 남은 목록을 출력합니다.
8. **빌린 데이터**: 사이클론처럼 PoE1 데이터를 빌린 항목에는 `borrowedFrom: "poe1-3.30"`을 붙입니다. 1.0 반영(P7) 뒤 빌린 항목이 남아 있으면 팩 빌드가 실패합니다.
9. **P2 전 최소 세트**(2026-11-24 고침): P2에서 DLL 검사를 켜기 전에 팩 `meta`·빌드 ID·`manifest.json`이 있어야 합니다. 이것은 P1b에서 **세대 0(지금의 PoE1 팩 세 개)** 기준으로 만듭니다. 세대 0 ESP는 표시 GLOB이 없는 것이 표시이므로(5.1 규칙 5), P2의 DLL 검사는 세대 0 구성으로 시험할 수 있습니다. 세대 GLOB과 `rules.json`은 세대 1 팩과 **같은 커밋에서** 넣습니다. 세대 1 내용 없이 GLOB만 먼저 넣으면 ESP는 세대 1, 팩은 세대 0인 어긋난 상태가 되기 때문입니다(1판·2판 초안은 P1 끝에 GLOB을 넣는다고 적었음).

## 4. 세이브 계약

### 4.1 레코드

| 레코드 | 내용 |
| --- | --- |
| `GENR` v1(새로) | `game`("poe2"), `contentGeneration`, `gameVersion`, `buildId`, 마지막으로 저장한 DLL 판, 내용 길이와 검사합(CRC32) |
| `MIGR` v1(새로) | 진행 중인 정리·이전의 상태. 출발·목표 세대, 단계 번호, 아직 원복하지 않은 체력·매지카 델타, 반환하지 못한 물건 목록, 환불 기록(종류·양·완료 여부), 시작 지급 완료 여부, 강제 종료할 지도 회차의 귀환 정보 |

- 레코드 판과 콘텐츠 세대는 따로 관리합니다. 레코드 판을 올려도 직전 판 읽기 경로는 남깁니다. MAPS가 v1·v2를 읽는 것(`MapSave.h:131-139`)과 같습니다.
- `GENR`은 정리·이전이 끝났을 때만 목표 세대로 씁니다. 그 전에는 `MIGR`이 있습니다.

### 4.2 판정

로드 때(`OnLoad`, 메모리 작업만) 다음 순서로 판정합니다. 판정 전에는 콘텐츠 검증(트리 정화, 지도 어픽스 대조)을 하지 않습니다.

| 경우 | 조건 | 처리 |
| --- | --- | --- |
| 새 게임 | SKSE `kNewGame` 메시지(`main.cpp:301-308`) | 정상 모드. 첫 저장에 `GENR` |
| 정상 | 온전한 `GENR`, 세대 = 팩 세대, `MIGR` 없음 | 정상 모드 |
| 진행 중 | 온전한 `MIGR` | 그 단계부터 이어서(4.4·4.5) |
| PoE1 세이브 | `GENR`·`MIGR` 없음, 온전한 CORE v2가 있음 | 정리 후 초기화(4.4) |
| 세대 이전 | 온전한 `GENR`, 세대 < 팩 세대 | 4.5 |
| 기록 없음 | SPOE 레코드가 하나도 없고 새 게임 메시지가 아님 | 기존 캐릭터에 처음 설치한 것으로 봅니다(델타 0이 맞음). 정상 모드로 켜되 "이 세이브에 모드 기록이 없어 처음 설치로 봅니다"를 알립니다. `.skse`를 잃은 경우와 구분할 수 없다는 한계를 문서·알림에 적습니다 |
| 판정 불능 | `GENR`이 잘렸거나 검사합 불일치, 미지원 판, `game`이 다름, 세대 > 팩 세대, `GENR`과 PoE1 CORE v2가 함께 있는 등 모순, CORE v2의 델타를 믿을 수 없음(4.3) | 보존 모드(4.6) |

### 4.3 CORE v2와 델타

- CORE v2 읽기 경로는 지우지 않습니다. 지금은 v2만 받고 판이 다르면 건너뛰므로(`SaveLoad.cpp:753`), 판을 올리며 이 경로를 지우면 델타가 0으로 읽혀 옛 보정이 기준값에 섞입니다.
- **델타는 따로 판정합니다.** 지금은 뒤쪽 젬 하나가 잘려도 임시 CORE 전체를 버리고, 유한하지 않은 델타는 0으로 바꿉니다(`SaveLoad.cpp:763-800`). 세대 0 정리용 읽기는 다음 순서를 따릅니다.
  1. 앞부분(레벨부터 델타까지)을 먼저 읽습니다.
  2. 델타가 유한하고 |델타| ≤ 현재 영구값이면 "믿을 수 있음"으로 봅니다. 그 범위를 벗어나면 "믿을 수 없음"이고, 0으로 바꾸지 않고 판정 불능으로 넘깁니다.
  3. 나머지(스킬 칸)는 따로 판정합니다. 칸이 깨져도 델타 판정은 유지합니다.
- **원복**: `kPermanent`에 음의 누적치를 줍니다. 현재 체력이 1 아래로 떨어지지 않게 보호합니다. 선례는 안전 제거입니다(`MapDeviceRuntime.cpp:3229-3246`).

### 4.4 PoE1 세이브 정리 후 초기화 (결정 190)

- **실행 방식**
  - 각 단계는 로드 뒤 주 갱신 스레드에서 `RunSerializedTransaction` 안에서 합니다. 안전 제거(`MapDeviceRuntime.cpp:3154-3161`)처럼 엔진 작업의 결과를 확인한 뒤 `MIGR`을 갱신하므로, 저장은 단계 전이나 후 하나만 봅니다.
  - 실패한 항목은 `MIGR`에 남겨 다음 틱에서 다시 시도합니다.
- **모드**: 정리 동안은 정리 대기 모드(4.6)입니다.

| 단계 | 할 일 |
| --- | --- |
| 0 | `MIGR`을 만듭니다(출발 0, 목표 = 팩 세대). PoE1의 지도 회차 귀환 정보, 델타, 끼운 물건 목록을 콘텐츠 검증 없이 옮겨 둡니다. 지금 MAPS 로더는 진행 중 회차의 어픽스를 새 팩과 대조해 맞지 않으면 회차 전체를 지웁니다(`SaveLoad.cpp:1145-1163`). 세대 0에서는 이 대조를 건너뜁니다 |
| 1 | **지도 회차 강제 종료**: 지도 셀 안·밖, 던전 팩의 일치 여부와 관계없이 진행 중 회차를 닫습니다. 지금의 호환 불가 분기는 던전 폼이 없을 때만 실행됩니다(`MapDeviceRuntime.cpp:3889`). 스폰 정리, 공물 환불(지금의 억제 조건 유지: 보스 처치·실패 회차는 환불 없음), 귀환 요청을 하고, 안전한 셀에 실제로 도착한 것을 확인한 뒤 완료로 기록합니다. 환불 결과는 `MIGR`에 먼저 적습니다 |
| 2 | **끼운 젬 반환**: 스킬 칸의 젬을 자식(보조)부터 실물로 돌려줍니다. 지금 안전 제거의 처리(`MapDeviceRuntime.cpp:3082-3098,3187-3196`)를 쓰고, 조회는 세대 0 반환표를 씁니다. 재시도할 수 있는 실패는 칸에 남깁니다 |
| 3 | **보조 젬이 든 가방 속 젬**: GKEY에서 자식을 품은 부모 젬을 찾아 자식을 실물로 떼어 냅니다. 플레이어 인벤토리와 지금 불러온 컨테이너만 처리합니다. 그 밖의 부모 젬은 자식 정보를 잃고, 그 목록을 로그에 남깁니다(한계) |
| 4 | **주얼·참 반환**: 소켓 주얼과 참은 실물로 돌려줍니다. **반지2·벨트는 실물이 이미 가방에 있으므로** 가상 참조만 해제합니다(`CraftingRuntime.cpp:1304-1398`, 안전 제거 `MapDeviceRuntime.cpp:3255-3259`). 물건을 더 만들지 않습니다 |
| 5 | **엔진 상태 원복**: 델타 원복(4.3), 대리 주문 제거(`ProxySpellRuntime.cpp:615`), Variable09 = 0, ES 풀·스탯 계층 비우기. 델타는 원복 직후 `MIGR`의 "미원복 델타"를 0으로 적습니다 |
| 6 | **SPDM·WDRP**: SPDM은 비우지 않고 남은 항목을 계속 저장해 다시 시도합니다(`SaveLoad.cpp:97-103,664-683`). WDRP는 항목마다 완료·재시도·시체 소실을 구분해 처리합니다. 지금 일괄 함수는 개별 결과를 버리므로(`WorldDropTracker.cpp:567-575`) 고칩니다 |
| 7 | **코세이브 상태 비우기**: CORE(레벨·경험치·칸), GKEY, TREE, ITEM 추적, SPRT, GEAR, ATLS, MAPS를 비웁니다 |
| 8 | 가방의 구판 물건은 지우지 않고 "(구판)" 표시로 둡니다(결정 194, 폐기 폼은 5.1 규칙 3). PoE2 시작 물건을 한 번 주고(결정 195) 지급 완료 여부를 `MIGR`에 적습니다 |
| 9 | `GENR`을 목표 세대로 쓰고 `MIGR`을 지웁니다. 화면 알림과 로그를 남깁니다 |

같은 세이브를 다시 불러오면 `MIGR`의 단계부터 이어 가므로, 앞서 끝낸 단계는 되풀이하지 않습니다.

### 4.5 세대 이전 (0.5 → 1.0 등, 결정 190)

1. **대응표**: `data/migrations/gen<N>-to-gen<N+1>.json`입니다.
   - 머리에 출발·목표 세대와 종류 목록을 둡니다.
   - 출발 세대의 콘텐츠 ID를 **빠짐없이** 적어야 합니다. 빠진 것이 있으면 팩 빌드가 실패합니다(런타임의 일괄 환불로 메우지 않음).
   - 여러 세대를 건너뛸 때는 중간 표를 차례로 적용합니다. 표가 없으면 판정 불능으로 처리합니다.
2. **필드별 처리**: 세이브에 의미가 담긴 모든 필드에 유지·변환·재검증·초기화 중 하나를 정합니다.

   | 필드 | 처리 |
   | --- | --- |
   | 클래스·전직 | 먼저 옮김. 사라진 전직은 전직 포인트 환불 |
   | TREE 노드와 GEAR 소켓 키 | 함께 옮김. 두 옛 소켓이 한 새 소켓으로 합쳐지면 밀려난 주얼은 가방으로 |
   | 마스터리 | 세대 1부터 없음 |
   | 스킬 칸의 젬 | `retire`면 칸에서 빼 실물 반환, 연결된 발동 칸·오라 비트도 해제 |
   | GKEY 중첩 보조 | 부모와 같은 규칙. `retire`된 자식은 떼어 실물로 |
   | 어픽스(장비·장착 주얼·지도 아이템) | `keep`은 값 배열 구조가 같을 때만, 구조가 바뀌면 재검증 후 범위 밖이면 다시 굴림. `retire`는 지움 |
   | 고유 ID | `retire`면 결정 194와 같은 구판 처리 |
   | 주얼 색, 무기 태그, 부위군 | 표대로 변환 |
   | 참 종류·충전 | 표대로 변환, 사라진 종류는 실물 반환 |
   | 아틀라스 이정표 | 유지 |
   | 가방의 지도와 진행 중 지도 회차 | 지도 아이템은 어픽스 규칙, 진행 중 회차는 4.4 단계 1처럼 강제 종료 |

3. **환불**: 종류별로 환불 단위·받는 곳·상한·중복 방지를 대응표에 적습니다. 노드 삭제 뒤의 포인트 재계산(`PassiveTree.cpp:326-399`)은 지출 환불과 항상 같지 않으므로, 환불액은 옛 할당에서 미리 계산해 `MIGR`에 적은 뒤 지웁니다.
4. **순서**: 대응표 적용 → 정화(`PassiveTree.cpp:961-1080`) → 포인트 재계산입니다. 정화는 클래스·전직·연결·허브까지 보므로(`:968-1005,1035-1080`), 클래스·전직을 먼저 옮겨야 할당 전체가 지워지지 않습니다.
5. **실행**: 4.4와 같이 `MIGR`로 단계를 기록하고, 끝나면 `GENR`을 목표 세대로 씁니다. 이미 끝난 이전은 아무것도 하지 않습니다.

### 4.7 옛 DLL로 내려갈 때

- 4.2의 "세대 > 팩 세대 → 보존"은 **이 규칙을 구현한 DLL부터** 지켜집니다.
- 이미 배포된 PoE1 DLL은 `GENR`을 모르기 때문에, 읽고 넘긴 뒤 다음 저장에서 지웁니다(`SaveLoad.cpp:1164-1166`). 새 ESP 대신 옛 ESP를 쓰면 새 폼도 사라집니다.
- 따라서 PoE1 판으로 되돌릴 때 복구할 수 있는 것은, 그 판에서 만든 `.ess`·`.skse` 쌍뿐입니다. 배포 안내(README)에 "PoE2 판으로 올리기 전에 세이브를 백업하라"를 넣습니다.

## 5. ESP 계약 (결정 192)

### 5.1 규칙

1. **장부**: `esp/formid-ledger.json`이 ESP 폼의 유일한 기준입니다.
   - 항목: FormID, EditorID, 레코드 타입, 분류, 콘텐츠 ID(세대 1부터), 세대 0 저장 키(`legacyKey`), 상태(`active`·`retired`), 도입 세대, 폐기 세대, 첫 분류(`keep`·`keep-candidate`·`retire-candidate`·`undecided`).
   - 머리: 플러그인 이름, 마스터 목록, 현재 콘텐츠 세대, 범위표와 그 상태(`proposed`·`approved`).
2. **배포 기준선**: 배포한 세대마다 장부 사본을 `esp/formid-ledger.published/gen<N>.json`으로 고정합니다. 검사기는 지금 장부가 모든 기준선에 대해 다음을 지키는지 봅니다.
   - 항목 삭제 없음
   - FormID와 EditorID의 대응 변경 없음(맞바꿈 포함)
   - 번호 재사용 없음
   - `retired → active` 되돌리기 없음
   - `legacyKey` 변경 없음
3. **폐기 폼은 지우지 않습니다.**
   - FULL 이름 앞에 "(구판) "을 붙입니다.
   - 플러그인은 폐기 폼에 기능을 주지 않습니다(화폐 사용, 감정, 장착, 지도 입장, 드랍 불가). 반환용 조회에만 남습니다.
4. **새 폼 범위** [제안, 장부의 범위 상태는 `proposed`]: 지금 쓰는 범위는 0x800~0x8BF입니다. 새 폼은 종류별로 묶어 할당합니다. ESL 상한은 0xFFF이고, HEDR 1.70에서도 0x800~0xFFF입니다(6.5단계 계획 3.2의 기록).

   | 범위 | 종류 |
   | --- | --- |
   | 0x900~0x9FF | 젬 |
   | 0xA00~0xA3F | 화폐 |
   | 0xA40~0xAFF | 봉인 토큰 |
   | 0xB00~0xB7F | 벨트·주얼·참·장비 베이스 |
   | 0xB80~0xBBF | 지도·웨이스톤·공물 |
   | 0xBC0~0xBFF | 효과 |
   | 0xC00~0xC0F | 표시(세대 GLOB 등) |
   | 0xC10~0xFFF | 예비 |

5. **세대 표시**
   - ESP에 GLOB `SPOE_ContentGeneration`을 0xC00에 둡니다. 숫자 타입은 short이고, 값은 콘텐츠 세대입니다.
   - 세대 0 ESP에는 이 GLOB이 없으며, 그 자체가 세대 0의 표시입니다.
6. **판별은 장부에서 만든 표로 합니다.**
   - 장부에서 `FormIds` 표를 생성합니다(손으로 고치지 않음).
   - 이 표를 쓰는 곳을 모두 바꿉니다.
     - 정방향·역방향 조회와 분류 순회: 화폐, 토큰, 벨트, 주얼 색, 참, 지도 티어(`FormIds.h:199-250`)
     - 시작 지급, 드랍
     - 제작 UI의 토큰 열거(`CraftingRuntime.cpp:598-621`)
     - 지도 입장(`MapDeviceRuntime.cpp:2837`)
     - 젬 역매핑(`GemInventory.cpp:621-649`)
   - 단일 MISC 조회 시험만으로는 회귀를 잡지 못하므로, 소비자마다 시험합니다.
7. **검사**
   - **빌드 때**(Python, ESP 바이트): 다음을 확인합니다.
     - 플러그인 이름과 마스터 목록(지금 `Skyrim.esm` 하나)
     - TES4의 ESL 플래그
     - 모든 장부 폼의 소유 바이트 = 자기 인덱스(마스터 수)
     - Deleted 플래그(0x20) 없음
     - ESP와 `records.json` 안에서 FormID·EditorID 중복 없음
     - 장부와 ESP·`records.json`의 FormID·EditorID·타입 일치
     - 폐기 폼의 "(구판) " 이름
     - 세대 GLOB의 타입과 값
     - 기준선 규칙(규칙 2)
     - 장부 필드의 일관성: 도입 ≤ 폐기 ≤ 현재, `active`에는 폐기 세대 없음, 새 폼은 승인된 범위·분류 안
   - **런타임**: `TESObjectMISC`는 `GetFormEditorID()`가 빈 문자열이라(`TESForm.h:175`, `TESObjectMISC.h:17`) 런타임 EditorID 비교는 하지 않습니다. 대신 다음을 확인합니다.
     - 디스크 ESP 해시와 `manifest.json`(3장 4)
     - 장부 폼마다 폼의 존재, 타입, 소유 파일
     - 삭제 상태가 아님
     - 하나라도 어긋나면 보존 모드
   - `VerifyEspForms`(`main.cpp:81-167`)는 이 규칙으로 바꿉니다.
