# 프로토타입 4: 패시브 트리 렌더

상태: 브라우저 단계 마침(2026-11-12). 게임 안(Prisma UI) 시험 네 번(2026-11-13)으로 이 프로토타입이 물은 것에 답이 나옴. 화면은 뜨고 그림도 다 불러옴. 가만히 있을 때는 게임의 프레임을 먹지 않음(60 FPS 그대로). 움직이는 동안에는 게임 전체의 프레임이 떨어짐: 화면 3840x2160에서 캔버스를 그대로 그리면 평균 25~27 FPS(실패), 캔버스를 1920x1080으로 그려 늘리면 38~47 FPS(조건부). 검색은 5ms 안. 한글 입력은 Prisma UI의 조합 상태 이벤트를 화면이 직접 그려 주면 됨(확인). 다만 SimpleIME가 켜져 있으면 영문만 들어감(확인). 남은 것은 설계 결정: 캔버스 해상도와 프레임 목표(설계-현황 5장 34번), SimpleIME와 함께 쓰는 방법(35번).

통합 설계서 14장의 6번("패시브 트리 렌더")에 해당합니다. 폴더 번호가 4인 것은 만든 순서입니다.

## 무엇을 확인하는가

PoE 3.29의 패시브 트리를 원본 규모로 쓰기로 했습니다(결정 6, 27). 화면은 Prisma UI로 만들 계획인데, Prisma UI는 CPU로 그리고 WebGL이 없습니다. 그래서 다음을 실행으로 확인합니다.

- 노드 수천 개의 트리를 Canvas 2D로 그려서 끊기지 않게 움직이고 확대·축소할 수 있는가.
- 통합 설계서 12.2의 3단 구성(미리 그린 바닥 타일, 찍은 노드와 강조의 덧그림, HTML 툴팁과 검색)이 필요한가, 매 프레임 다 그려도 되는가.
- 검색이 입력을 따라올 만큼 빠른가. 한글 입력이 되는가.

## 통과 기준

게임 안에서 재기 전에 정한 기준입니다. 숫자는 게임 안(Prisma UI)에서 잰 값에 적용합니다. 브라우저에서 잰 값은 그 전 단계의 참고입니다.

| 항목 | 통과 | 조건부 | 실패 |
| --- | --- | --- | --- |
| 움직이는 동안의 프레임 | 평균 55 FPS 이상, 가장 느린 1%가 30 FPS 이상 | 평균 30~55 FPS | 평균 30 FPS 미만 |
| 가만히 있을 때 | 다시 그리지 않음(게임의 프레임을 먹지 않음) | | 계속 그림 |
| 모양 | 노드 위치와 연결선(직선, 호)이 PoB와 같음 | | 어긋남 |
| 노드를 찍었을 때의 반영 | 다음 프레임 | | 눈에 보이게 늦음 |
| 검색 | 글자를 칠 때마다 결과가 100ms 안에 표시됨 | | 그보다 늦음 |
| 한글 입력 | 검색창에 한글이 조합되어 들어감 | 조합이 깨지지만 붙여 넣기는 됨 | 입력 불가 |

## 구성

- `tools/convert_tree.py`: PoB의 `TreeData/3_29/tree.lua`와 `sprites.lua`를 읽어 화면용 데이터로 바꿉니다. 노드의 최종 좌표, 연결선의 호 정보, 아이콘 좌표를 여기서 미리 계산합니다(통합 설계서 4.2). Lua 데이터 표를 읽는 작은 파서가 들어 있습니다.
- `tools/build_site.py`: 화면 파일과 변환한 데이터를 `out/site/`에 모읍니다.
- `view/index.html`, `view/tree.js`, `view/tree.css`: 화면입니다. 바깥 라이브러리를 쓰지 않습니다.
- `plugin/`: 이 화면을 게임 안에서 Prisma UI 뷰로 띄우는 SKSE 플러그인(`PoEProtoTree.dll`)입니다. 아래 "게임 안 단계"를 참고하세요.

`out/`에는 GGG의 데이터와 그림(PoB에 든 것의 복사본)이 들어가므로 저장소에 넣지 않습니다(`.gitignore`의 `prototypes/*/out/`).

### 그리는 방식 두 가지

같은 화면에서 버튼으로 바꿔 가며 비교합니다.

- **직접**: 매 프레임 보이는 범위의 선과 노드를 전부 다시 그립니다.
- **타일**: 변하지 않는 바닥(배경, 선, 찍지 않은 노드)을 512픽셀 타일로 미리 그려 두고, 프레임마다 타일을 붙인 뒤 찍은 노드·검색 결과·가리킨 노드만 그 위에 그립니다. 타일은 배율 다섯 단계(0.04~0.64)로 필요할 때 만들고, 한 프레임에 6ms까지만 새로 그립니다. 아직 없는 타일은 더 거친 단계의 타일을 늘려서 대신 보여 줍니다. 최대 160장을 보관하고 오래 안 쓴 것부터 버립니다.

두 방식 모두 다음을 씁니다.

- 공간 격자(한 칸 800)로 화면에 걸리는 노드와 선만 고릅니다.
- 노드가 5픽셀보다 작게 보이면 그림 대신 점으로 그립니다.
- 움직임이 없으면 다시 그리지 않습니다.

## 실행

```bash
python -I prototypes/04-passive-tree/tools/build_site.py
```

```bash
python -I -m http.server 8765 --bind 127.0.0.1 --directory prototypes/04-passive-tree/out/site
```

브라우저에서 `http://localhost:8765/`를 엽니다. 끌어서 이동, 휠로 확대·축소, 노드를 눌러 찍기와 지우기, 검색창에서 Enter로 다음 결과로 이동합니다.

주소에 붙일 수 있는 값:

| 값 | 뜻 |
| --- | --- |
| `mode=direct` | 직접 방식으로 시작(기본은 타일) |
| `lod=0` | 작은 노드를 점으로 바꾸지 않음 |
| `tiles=N` | 보관할 타일 수(기본 160) |
| `dpr=1` | 화면 배율의 상한. 게임 안과 같게 1로 두고 잴 때 씀 |
| `cpu=1` | 캔버스를 GPU 가속 없이 만듦. CPU로 그리는 환경을 흉내 내려는 것 |
| `w=1920&h=1080` | 창 크기와 무관하게 그 크기로 그림 |
| `alloc=1` | 시작할 때 임의의 경로로 123포인트를 찍음 |
| `ui=2` | 글자와 버튼의 배율(0.5~4). 주지 않으면 화면 높이에 맞춤(1080이 1, 2160이 2) |
| `timer=1` | 화면 갱신 콜백 대신 타이머로 프레임을 돌림. 가려진 브라우저 창에서 측정 묶음의 흐름만 확인할 때 씀(숫자는 뜻이 없음) |
| `scale=0.5` | 캔버스의 내부 해상도를 화면보다 낮춰 그리고 늘려 보여 줌(0.25~1). 화면의 "해상도" 버튼으로도 전체와 절반을 오갈 수 있음 |
| `bench=1` | 시작할 때 측정을 한 번 돌림 |

측정은 화면의 "측정" 버튼이나 콘솔의 `PoETree.runBench()`로 돌립니다. 정해진 경로(멀리서 가로지르기, 확대, 가까이서 가로지르기, 축소, 확대·축소 반복, 모두 14.5초)로 화면을 움직이며 프레임 간격과 그리는 데 든 시간을 모읍니다. `PoETree.runSyncBench({mode: 'tiles'})`는 화면 갱신 주기와 무관하게 같은 경로를 1/60초 간격으로 밟으며 그리는 시간만 잽니다.

## 결과

### 데이터 (2026-11-12, PoB 2.67.2의 3.29 데이터)

- 원본의 노드는 3,396개이고, 그 가운데 트리에 놓이는 것은 **2,916개**입니다. 402개는 그룹이 없고(트리 위에 자리가 없는 노드), 78개는 프록시 노드입니다.
- 놓이는 2,916개의 구성: 일반 1,782, 주요 패시브 702, 키스톤 49, 마스터리 315, 주얼 소켓 24, 클래스 시작 7, 전직 시작 37. 이 가운데 전직 쪽 노드가 565개입니다(리그 전용 전직 포함).
- 연결선 2,856개(호 1,558, 직선 1,298), 배경이 있는 그룹 423개.
- 변환한 데이터는 636KB입니다. 그림 6장은 원본 그대로면 2.9MB이고, JPEG 두 장을 PNG로 바꾸면 8.1MB입니다. 변환에 0.4초가 걸립니다(PNG로 바꿀 때는 조금 더).

통합 설계서와 이 저장소의 다른 문서가 말하는 "3,396노드"는 원본의 노드 수이고, 화면에 그릴 수는 그보다 적습니다.

### 브라우저에서 잰 것 (2026-11-12)

조건: Claude 앱의 내장 브라우저(Chromium 156), 1920x1080, 화면 배율 1, GPU 가속 없는 캔버스(`cpu=1`), 123포인트를 찍은 상태, 작은 노드는 점으로. `runSyncBench`로 프레임 하나를 그리는 시간을 잼(경로의 프레임을 두세 개마다 하나씩).

| 방식 | 프레임 수 | 평균 | 95% | 99% | 최대 | 16.7ms를 넘긴 프레임 |
| --- | --- | --- | --- | --- | --- | --- |
| 타일(타일이 하나도 없는 상태에서 시작) | 435 | 4.5ms | 9.8ms | 11.5ms | 21.2ms | 1 |
| 타일(한 번 돈 뒤 다시) | 435 | 4.4ms | 9.0ms | 10.8ms | 39.7ms | 2 |
| 직접 | 290 | 7.7ms | 21.8ms | 32.9ms | 33.9ms | 21 |

- **타일 방식은 거의 모든 프레임이 60 FPS에 필요한 16.7ms 안에 들었습니다.** 직접 방식은 전체가 보이도록 축소했을 때 무너집니다(확대·축소 반복 구간에서 60프레임 중 16프레임이 16.7ms를 넘김). 가까이 확대했을 때는 직접 방식도 평균 3.4ms로 충분합니다.
- 측정 경로는 다섯 단계의 타일을 모두 지나가서 타일을 613장 새로 그렸습니다. 보관 한도 160장으로는 한 번 돈 뒤에도 553장을 다시 그렸습니다. 그래도 프레임 시간이 유지된 것은 한 프레임에 타일을 그리는 시간을 6ms로 묶어 두었기 때문입니다. 그 대신 타일이 채워지는 동안 거친 타일이 잠깐 보입니다.
- 검색은 2,916개를 훑는 데 0.2~1.5ms입니다. `키스톤` 49개, `주요` 702개, `maximum life` 158개, `resolute technique` 1개가 맞게 나왔습니다.
- 모양: 아이콘, 테두리, 그룹 배경, 직선과 호가 맞게 그려집니다(화면으로 확인). PoB의 화면과 나란히 놓고 대조하지는 않았습니다.

### 한계

- **이 숫자는 Prisma UI의 숫자가 아닙니다.** 브라우저의 CPU 캔버스와 Prisma UI의 렌더러는 다른 엔진입니다. 타일 방식이 직접 방식보다 유리하다는 방향은 믿을 만하지만, 게임 안에서 16.7ms 안에 드는지는 게임 안에서 재야 합니다.
- 타일은 한 장이 약 1MB(512x512, 픽셀당 4바이트)라, 보관 한도 160장을 다 채우면 약 168MB입니다. Prisma UI에서 이만큼을 쓸 수 있는지는 확인하지 않았습니다. 한도는 `tiles=`로 줄일 수 있습니다.
- 화면 갱신 주기에 맞춘 측정(`runBench`)은 하지 못했습니다. 측정에 쓴 브라우저 창이 가려져 있어 갱신이 느려졌기 때문입니다. 그래서 그리는 시간만 재는 방식을 썼습니다.
- 작은 노드를 점으로 바꾸지 않았을 때(`lod=0`)와 2560x1440에서는 재지 못했습니다(측정 중 브라우저 탭이 닫힘).
- 한글 입력은 브라우저에서는 확인할 필요가 없고(브라우저는 됨) 게임 안에서 봐야 합니다. 지금 한글로 찾을 수 있는 것은 노드의 종류 이름(키스톤, 주요 패시브, 마스터리, 주얼 소켓)뿐입니다. 노드 이름과 효과의 한글은 아직 없습니다.
- 찍기는 아무 노드나 눌러 켜고 끄는 것뿐입니다. 시작점에서 이어져야 한다는 규칙, 포인트 수, 마스터리 선택, 전직은 이 프로토타입의 범위가 아닙니다.
- 전직 트리는 데이터에 적힌 자리(본 트리의 바깥)에 그대로 그립니다. 게임처럼 가운데로 옮겨 보여 주지 않습니다.
- 게임패드 조작은 없습니다.

## 게임 안 단계 (2026-11-12 만들어 배치함, 2026-11-13 1차 시험)

브라우저의 숫자는 Prisma UI의 숫자가 아니므로, 같은 화면을 게임 안에서 띄워 같은 측정을 돌립니다. 사용자가 "게임을 켜 가며 하나씩 시험하면 오래 걸린다"고 했으므로, 게임을 한 번 켜서 필요한 숫자를 모두 얻도록 만들었습니다.

### 동작

- `plugin/`의 DLL(`PoEProtoTree.dll`)이 게임 데이터가 불린 뒤 Prisma UI 뷰 하나(`PoEProtoTree/index.html`)를 만들고 숨겨 둡니다.
- INI의 `ToggleKey`(기본 F6)를 누를 때마다 다음으로 넘어갑니다: 닫힘 → **게임을 멈추고 열기** → **게임을 돌린 채 열기** → 닫힘.
- 열릴 때마다 화면이 측정을 스스로 돌립니다(단계마다 약 36초). 순서는 이렇습니다. 진행 상태는 화면 오른쪽 아래에 표시됩니다.
  1. 기준(3초): 트리를 그리지 않을 때의 프레임 간격. 게임 자신의 몫입니다.
  2. 기준(3초): 캔버스의 점 몇 개만 바꿀 때. 화면이 조금이라도 바뀌면 드는 고정 비용(화면 전체 복사)을 봅니다.
  3. 타일 방식, 화면 그대로의 해상도(14.5초).
  4. 타일 방식, 가로·세로 절반 해상도(14.5초). 낮춰 그린 그림을 화면 크기로 늘려 보여 줍니다.
  5. 검색 시간과, 기준에 견주어 프레임마다 더해진 시간의 요약.
- 모든 측정은 화면 갱신에 맞춰 돌아 게임을 세우지 않습니다. 1차 시험에 있던 "그리는 시간만 재는 측정"과 직접 방식의 측정은 게임 안 묶음에서 뺐습니다(앞의 것은 게임을 5~6초씩 멈췄고, 직접 방식은 1차에서 이미 타일보다 느린 것이 나왔습니다).
- "게임을 멈추고 열기"의 측정이 끝나면 화면이 스스로 다음 단계로 넘어가 "게임을 돌린 채 열기"를 이어서 잽니다. F6을 한 번 누르면 두 단계가 모두 측정됩니다(약 75초).
- 한 번 잰 단계는 그 실행 동안 다시 재지 않습니다. 닫았다가 다시 열면 측정 없이 바로 만져 볼 수 있습니다.
- 측정 도중에 F6을 눌러도 됩니다. 하던 측정을 버리고 새 단계에서 처음부터 다시 잽니다.
- INI의 `LogSearchInput = true`로 두면 검색창에서 일어난 일(포커스, 들어온 글자, 조합 중인 글자)이 로그에 `검색창: …`으로 남습니다. 친 글자가 그대로 남으므로 기본은 꺼져 있습니다.
- 닫으면 타일을 모두 버립니다(한 장에 약 1MB). 다시 열면 몇 프레임에 걸쳐 다시 만듭니다.
- 닫으면 화면이 측정과 화면 갱신을 스스로 멈춥니다(Prisma UI는 숨긴 뷰의 스크립트도 계속 돌리기 때문).
- 결과는 화면이 DLL로 보내고, DLL이 `Documents\My Games\Skyrim Special Edition\SKSE\PoEProtoTree.log`에 남깁니다. 사람이 읽는 요약 줄과 자세한 값(JSON)이 함께 남습니다.

### 시험 방법

1. MO2에서 `[PoE Proto] 4 Passive Tree`를 켜고 게임을 실행해 세이브를 불러옵니다.
2. 안전한 곳에서 F6을 누릅니다. 게임이 멈추고 트리 화면이 뜨며 측정이 시작됩니다. 화면이 스스로 움직입니다.
3. 그대로 둡니다. 약 36초 뒤 화면이 스스로 "게임을 돌린 채 열기"로 넘어가 같은 측정을 한 번 더 합니다(이 동안 게임이 돕니다). 오른쪽 아래에 "측정이 모두 끝났습니다"가 뜨면 끝입니다.
4. F6으로 닫았다가 다시 F6으로 엽니다(이번에는 측정 없이 게임을 멈춘 채 열립니다). 직접 만져 봅니다. 끌어서 이동, 휠로 확대·축소, 노드를 눌러 찍기, 노드에 올려 툴팁 보기. "해상도" 버튼을 눌러 절반 해상도가 얼마나 흐려 보이는지도 봅니다.
5. 검색창을 눌러 한글로 `키스톤`을 쳐 봅니다. 조합 중인 글자는 검색창 바로 아래의 작은 상자에 보이고, 글자가 확정되면 검색창에 들어갑니다. 안 되면 영문이 대신 들어가는지, 아무것도 안 들어가는지를 봅니다.
6. F6을 두 번 눌러(돌린 채 열기 → 닫기) 또는 "닫기"로 닫습니다.

화면에서 볼 것: 그림과 글자가 깨지지 않는지, 움직일 때 끊기는지, 게임을 돌린 채 열었을 때 게임이 눈에 띄게 느려지는지, 가만히 둘 때는 어떤지.

- 화면이 입력을 쥔 동안에도 게임 쪽 키 입력(F6)이 플러그인에 온다는 것. 안 오면 화면의 버튼을 씁니다.
- `Focus`를 풀었다가 다시 걸어 "멈춤"과 "돌림"을 바꿀 수 있다는 것.
- Prisma UI에서 화면 갱신 콜백이 초당 60번 온다는 것, 그리고 그리는 시간만 재는 측정이 Prisma UI에서도 뜻이 있다는 것(그리기 명령을 모아 두었다가 나중에 한꺼번에 그리는 구조라면 실제보다 짧게 나옵니다. 그래서 화면 갱신에 맞춘 측정을 기준으로 봅니다).
- 타일 160장(최대 약 168MB)을 Prisma UI가 감당한다는 것.

### 1차 시험 결과 (2026-11-13)

환경: AE 1.6.1170, Prisma UI 1.5.1(GitHub `PrismaUI-SKSE/framework`의 1.5.1 배포판. 로그에 찍힌 소스 줄 번호가 공개 소스와 일치함), 화면 3840x2160, 배율 1, Ultralight 1.4.1. 같은 UI 스레드에 다른 모드의 뷰가 3개 더 있었습니다.

세 번 열었고, 측정 도중에 F6을 누르지 않은 것은 세 번째의 "게임을 멈추고 열기"뿐입니다. 첫 번째는 화면 갱신 기준 측정 둘까지는 온전합니다.

| 측정 (게임을 멈추고 엶, 3840x2160) | 타일 방식 | 직접 방식 |
| --- | --- | --- |
| 움직이는 동안 평균 | 31.3 / 31.6 FPS | 24.6 / 24.8 FPS |
| 가장 느린 1% | 19.6 / 20 FPS | 16.4 / 16.7 FPS |
| 프레임 간격 평균 | 31.9 / 31.6ms | 40.7 / 40.2ms |
| 그중 우리 코드가 그리는 시간 평균 | 14.2 / 14.4ms | 22.9 / 22.9ms |
| 간격에서 그리는 시간을 뺀 나머지 | 17.8 / 17.2ms | 17.8 / 17.3ms |

(값은 첫 번째 / 세 번째 시험.)

통과 기준으로 보면 타일 방식은 **조건부**(평균 30~55 FPS)의 아래 끝이고 가장 느린 1%는 통과선(30 FPS)에 못 미칩니다. 직접 방식은 **실패**(평균 30 FPS 미만)입니다. 브라우저에서 잰 것(1920x1080, 타일 평균 4.5ms)보다 그리는 시간이 3배쯤 길고, 화면의 점 수는 4배입니다.

확인된 것:

- **트리를 그리는 시간은 게임의 프레임 시간에 그대로 더해집니다.** Prisma UI의 소스(`src/PrismaUI/Core.cpp`의 `D3DPresent`)를 보면, 게임이 프레임을 내보낼 때마다 UI 스레드에 "스크립트 실행, 그리기, 화면으로 복사"를 맡기고 그것이 끝날 때까지 게임의 렌더 스레드가 기다립니다. 화면 갱신 콜백은 게임의 프레임마다 한 번 옵니다(초당 60번으로 고정된 것이 아님). 위 표에서 "나머지"가 구간과 방식에 관계없이 17~18ms로 일정한 것이 이것과 맞습니다. 그 나머지는 게임 자신의 프레임 시간과, Ultralight가 캔버스를 화면에 올리는 시간(바뀐 프레임마다 3840x2160 그림 전체를 두 번 복사)이 합쳐진 값이고, 이번 측정으로는 둘을 나누지 못합니다.
- 그래서 스크립트가 오래 걸리면 게임 전체가 그만큼 멈춥니다. 이번 측정 묶음의 3/4, 4/4 단계(그리는 시간만 재는 측정)는 각각 5~6초 동안 게임을 멈춰 세웠습니다. 이 단계가 끝난 순간에야 밀려 있던 F6이 처리된 것이 로그에 남아 있습니다. 측정 도구의 결함이고, 게임 안 측정에서는 빼야 합니다.
- 뷰를 숨겨도(`Hide`) 스크립트와 화면 갱신 콜백은 같은 속도로 계속 돕니다(숨긴 뒤의 측정 구간에서 평균 23~30 FPS가 그대로 나옴). 소스에서도 숨긴 뷰는 화면으로 복사하는 것만 건너뜁니다. 닫은 동안에는 화면 쪽에서 일을 멈춰야 합니다.
- 게임 데이터가 불린 직후에 뷰를 만들 수 있습니다. 화면의 준비 완료 콜백은 메인 메뉴가 뜬 뒤에 왔습니다(약 19초 뒤. Prisma UI의 로그로는 화면 자체는 0.1초 안에 준비됨).
- 그림 6장(PNG)은 모두 불러왔습니다(93ms). JPEG를 그대로 넣었을 때 되는지는 재지 않았습니다.
- 화면이 입력을 쥔 동안에도 F6이 플러그인에 옵니다.
- `Focus(pauseGame=true)` 뒤에 `Unfocus`와 `Focus(pauseGame=false)`를 부르면 true가 돌아옵니다. 게임이 실제로 다시 돌았는지는 화면으로 확인해야 합니다(사용자 확인 전).
- `OffscreenCanvas`는 없습니다(문서의 지원 목록과 다름). 타일은 보통의 `canvas` 요소로 만들어지고 160장 한도까지 찼으며 오류는 없었습니다.
- `performance.now()`는 1ms 단위로만 나옵니다. 검색 시간이 0.0, 1.0, 3.0ms로 찍힌 것은 그 때문이고, 100ms 기준에는 여유가 있습니다.

확인하지 못한 것:

- **게임을 돌린 채 열었을 때의 숫자.** 측정 도중에 F6을 누르면 단계만 넘어가고 측정은 앞 단계의 이름으로 계속 돌았습니다(측정 도구의 결함). 세 번째 시험의 "돌린 채 열기"는 측정이 시작된 지 2초 만에 닫혀, 남은 한 줄(평균 29.5 FPS)은 대부분 화면을 숨긴 상태에서 잰 값입니다.
- 한글 입력. 로그에 조합 기록이 없습니다. 쳐 보지 않은 것인지 조합 이벤트가 오지 않은 것인지 로그로는 가를 수 없습니다.
- 화면의 모양(그림과 글자), 손으로 움직였을 때의 느낌. 사용자가 본 것을 들어야 합니다.
- 화면이 열려 있지 않을 때의 게임 프레임 시간. 위 "나머지" 17ms를 나누려면 필요합니다.
- 캔버스의 내부 해상도를 낮췄을 때(예: 1920x1080으로 그리고 늘려 보여 주기) 얼마나 빨라지는지.

통과 기준에 대해: "평균 55 FPS 이상"은 이 구조를 모르고 정한 숫자입니다. 화면의 프레임은 게임의 프레임보다 높을 수 없고, 게임이 60 FPS로 돌 때 55 FPS를 내려면 프레임당 UI 작업 전체가 1.5ms 안이어야 합니다. 기준을 바꿀지는 정하지 않았습니다(설계-현황 5장 34번).

### 1차 시험 뒤에 고친 것 (2026-11-13, 2차 시험 전)

사용자 선택 "고치고 다시 재기"에 따라 고쳐 다시 배치했습니다. 브라우저에서 게임 쪽 호출을 흉내 내어 묶음이 끝까지 도는 것, 도중에 단계를 바꾸거나 닫으면 버리고 정리하는 것을 확인했습니다. 게임 안에서는 아직 돌려 보지 않았습니다.

- 게임을 멈추던 측정을 빼고, 기준 측정 둘과 절반 해상도 측정을 넣었습니다(위 "동작").
- 측정 도중에 단계가 바뀌면 하던 측정을 버리고 새 단계에서 다시 잽니다. 로그에 `측정 중단: 단계가 바뀜`이 남습니다.
- 닫을 때 DLL이 화면에 알리고(`poeTreeOnHide`), 화면은 측정과 화면 갱신을 멈춥니다. 다시 열면 이어서 돕니다.
- 결과 줄에 그린 해상도(예: `타일 3840x2160`, `타일 1920x1080`)가 찍히고, `요약` 줄에 기준 간격과 거기에 더해진 시간이 나옵니다.

2차 시험에서 볼 것: 기준 간격(게임 자신의 프레임 시간)이 얼마인지, 점 몇 개만 바꿔도 드는 시간이 얼마인지, 절반 해상도에서 더해지는 시간이 얼마나 줄어드는지, 게임을 돌린 채 열었을 때는 어떤지. 절반 해상도의 그림이 Prisma UI에서 어떻게 늘려 보이는지(흐림 정도)는 화면으로 봐야 합니다.

Prisma UI의 인터페이스 선언(`plugin/src/PrismaUIApi.h`)은 Prisma UI가 배포하는 `PrismaUI_API.h`("PrismaUI modder API - do whatever you want with it.")를 옮긴 것입니다. 이 컴퓨터의 다른 프로젝트에 들어 있는 사본을 보고 옮겼습니다.

### 2차 시험 결과 (2026-11-13)

사용자가 "게임을 멈추고 열기"의 측정을 끝까지 돌렸고, "게임을 돌린 채 열기"는 하지 않고 닫았습니다. 사용자가 본 것: **검색창에 한글이 안 쳐짐. 메뉴가 너무 작게 보임.**

| 측정 (게임을 멈추고 엶, 화면 3840x2160) | 캔버스 3840x2160 | 캔버스 1920x1080(늘려 보여 줌) |
| --- | --- | --- |
| 움직이는 동안 평균 | 34.1 FPS | 50.4 FPS |
| 가장 느린 1% | 21.7 FPS | 33.3 FPS |
| 프레임 간격 평균 | 29.3ms | 19.9ms |
| 그중 우리 코드가 그리는 시간 평균 | 14.1ms | 5.0ms |
| 간격에서 그리는 시간을 뺀 나머지 | 15.3ms | 14.9ms |

확인된 것:

- **캔버스를 절반 해상도로 그리면 그리는 시간이 3분의 1쯤으로 줄어듭니다**(14.1 → 5.0ms). 미리 정한 기준으로는 여전히 조건부(평균 30~55 FPS)이고, 가장 느린 1%는 통과선(30 FPS)을 넘습니다.
- **"나머지"는 캔버스 해상도와 관계없이 약 15ms입니다.** 게임 자신의 프레임 시간과, 캔버스 해상도와 상관없이 3840x2160인 뷰 표면을 화면에 올리는 시간이 합쳐진 값입니다. 이 둘은 이번에도 나누지 못했습니다(아래 결함 때문).
- **타일 결함: 화면이 크면 뒤쪽 타일이 끝내 만들어지지 않았습니다.** 타일을 새로 만드는 한도(프레임당 6ms)를 프레임이 시작된 뒤의 시간으로 쟀는데, 3840x2160에서는 이미 있는 타일을 그리는 데만 6ms가 넘게 걸려 뒤쪽 타일의 차례가 오지 않았습니다. 그래서 가만히 있을 때도 매 프레임 다시 그렸고(기준 측정 3초 동안 124번), **기준 측정 둘은 무효**입니다. 1차 시험과 이번의 3840x2160 숫자도 이 상태에서 잰 것입니다. 타일 한도 160장도 3840x2160에서 타일이 가장 작게 보일 때 필요한 수(187장)보다 작았습니다.
- 한글 입력: 로그에 조합 기록이 없습니다. Prisma UI의 소스와 `IME_SUPPORT.md`를 보니 **Prisma UI는 표준 조합 이벤트를 보내지 않습니다.** 조합 중인 글자는 입력창에 넣어 주지 않고 `prismaIME_state` 이벤트로 상태만 알려 주며, 화면이 그것을 직접 그려야 합니다. 확정된 글자만 보통의 글자 입력으로 들어옵니다. 우리 화면은 이 이벤트를 듣지 않았으므로 조합 중인 글자가 보이지 않았을 것은 확실합니다. 다만 확정된 글자까지 안 들어왔는지, 영문이 대신 들어갔는지는 로그에 남기지 않아 알 수 없습니다(원인 미확정).
- 작게 보인 것: 화면이 3840x2160에 배율 1로 뜨므로 14px로 적은 글자와 버튼이 1080p 화면의 절반 크기로 보입니다. 사용자가 말한 "메뉴"가 글자·버튼을 가리킨 것인지는 확인하지 않았습니다.

### 2차 시험 뒤에 고친 것 (2026-11-13, 3차 시험 전)

브라우저에서 3840x2160 크기로 띄워 확인했고, 게임 안에서는 아직 돌려 보지 않았습니다.

- 타일: 새로 만드는 한도를 "타일을 만드는 데 쓴 시간"으로 재고 프레임마다 적어도 하나는 만듭니다. 타일 한도는 화면을 덮는 데 필요한 수에 맞춰 늘립니다(3840x2160에서 200장, 절반 해상도에서는 160장 그대로). 이번 프레임에 쓴 타일은 버리지 않습니다. 그 결과 3840x2160에서는 타일을 실제로 다 만들게 되어, 움직이는 동안의 숫자가 2차보다 나빠질 수 있습니다(2차의 숫자는 타일 일부를 안 만든 채 잰 것).
- 한글 입력: `prismaIME_state`를 받아 조합 중인 글자와 후보를 검색창 아래에 그립니다. 조합 중인 글자도 검색에 반영합니다. 조합 중에는 Enter·Esc 단축키가 반응하지 않게 했습니다. 검색창의 포커스, 들어온 글자, 조합 상태를 로그에 남겨 다음 시험에서 어디까지 되는지 가를 수 있게 했습니다. **이것으로 한글이 들어가게 됐는지는 게임 안에서 확인해야 합니다.**
- 크기: 글자, 버튼, 여백, 툴팁을 화면 높이에 맞춰 키웁니다(1080이 1배, 2160이 2배). CSS 변수와 `calc`를 쓰는데 Prisma UI에서 그대로 되는지는 게임 안에서 봐야 합니다.
- 측정: 두 단계를 이어서 스스로 재고, 한 번 잰 단계는 다시 재지 않습니다(위 "동작").
- `hidden` 속성을 준 요소가 CSS의 `display` 때문에 보이던 것(브라우저에서 게임용 버튼이 보임)을 고쳤습니다.

3차 시험에서 볼 것: 기준 간격(게임 자신의 프레임 시간), 점 몇 개만 바꿔도 드는 시간, 타일을 다 만드는 상태에서의 3840x2160과 1920x1080의 숫자, 게임을 돌린 채 열었을 때의 숫자, 한글이 들어가는지와 로그의 `검색창:` 줄, 글자와 버튼의 크기.

### 3차 시험 결과 (2026-11-13)

사용자가 본 것: **`키스톤`을 한글로 치면 영문이 들어감. 글자와 버튼 크기는 괜찮음.**

"게임을 멈추고 열기"의 측정은 시작 3.4초 뒤에 단계가 넘어가 버려졌고(기준 측정 하나만 남음: 간격 17.2ms, 58.3 FPS), "게임을 돌린 채 열기"는 끝까지 돌았습니다. 아래는 게임을 돌린 채 잰 값입니다.

| 측정 (게임을 돌린 채 엶, 화면 3840x2160) | 값 |
| --- | --- |
| 기준: 트리를 그리지 않을 때 | 간격 16.5ms (60.6 FPS), 그 사이 다시 그린 횟수 0 |
| 기준: 캔버스의 점 몇 개만 바꿀 때 | 간격 17.6ms (56.9 FPS). 기준보다 +1.1ms |
| 타일, 캔버스 3840x2160 | 평균 24.8 FPS, 가장 느린 1% 16.9 FPS. 간격 40.4ms, 그중 우리가 그리는 시간 20.7ms |
| 타일, 캔버스 1920x1080 | 평균 38.1 FPS, 가장 느린 1% 27.0 FPS. 간격 26.3ms, 그중 우리가 그리는 시간 6.2ms |

확인된 것:

- **가만히 있을 때는 게임의 프레임을 먹지 않습니다.** 화면이 열려 있어도 트리가 바뀌지 않으면 60.6 FPS 그대로입니다. 통과 기준의 "가만히 있을 때" 항목은 통과입니다. 타일이 끝내 안 채워지던 결함도 고쳐졌습니다(다시 그린 횟수 0).
- **화면이 조금 바뀌는 것만으로 드는 고정 비용은 약 1ms입니다.** 3840x2160 그림 전체를 복사하는 값이 이 정도이므로, 느린 원인은 복사가 아니라 그리는 일 자체입니다.
- **움직이는 동안에는 게임 전체가 그 프레임으로 떨어집니다.** 프레임 간격은 대략 "기준 16.5ms + 우리가 그리는 시간 + 3~4ms"입니다. 3840x2160 그대로는 프레임마다 약 24ms, 1920x1080 캔버스로는 약 10ms가 더해졌습니다.
- 미리 정한 기준으로는 3840x2160 그대로가 실패(평균 30 FPS 미만), 1920x1080 캔버스가 조건부입니다.
- 2차의 3840x2160 숫자(멈춘 상태 34 FPS, 그리는 시간 14ms)보다 나빠진 것은 예상대로입니다. 2차는 타일 일부를 안 만든 채 잰 것이었습니다. 다만 2차는 게임을 멈춘 상태, 3차는 돌린 상태라 두 조건이 함께 바뀌었고, 각각의 몫은 나누지 못합니다.
- 글자와 버튼을 화면 높이에 맞춰 키운 것(CSS 변수와 `calc`)이 Prisma UI에서 동작합니다.

한글 입력 (원인 미확정):

- 확인된 사실 1: 로그에 `검색창: 입력값 'z'`, `'zl'`이 남았습니다. `ㅋ`, `ㅣ` 자리의 영문입니다. 조합 상태 이벤트(`prismaIME_state`)는 한 번도 오지 않았습니다. 즉 입력기가 조합을 시작하지 않았습니다.
- 확인된 사실 2: 이 모드 목록에 **SimpleIME 1.3.0**이 켜져 있고, 그 로그에 시작할 때 `IME window get focus`가 남습니다. 설정은 `Focus_Type = Permanent`, `Keep_Ime_Open = false`입니다.
- 소스로 본 것(공개 저장소의 v1.1.1. 설치된 1.3.0과 파일 구성은 같으나 같은 코드인지는 대조하지 못함): SimpleIME는 자기 창이 키보드 포커스를 쥐고, 키 입력을 게임 창으로 그대로 넘깁니다. 입력기는 게임의 글자 입력칸이 열려 있을 때(`ControlMap`의 글자 입력 수가 0보다 클 때)만 켭니다. 조합이 끝난 글자는 창 메시지가 아니라 게임의 Scaleform 메뉴로 보냅니다.
- 가설 A(유력): Prisma UI 화면이 열려 있어도 SimpleIME가 보기에는 글자 입력칸이 없으므로 입력기가 꺼져 있고, 키는 영문 그대로 넘어온다. Prisma UI가 게임 창에 입력기를 붙이는 처리는 포커스가 SimpleIME의 창에 있어 소용이 없다. 맞다면 SimpleIME를 끄면 한글이 들어가야 한다.
- 가설 B: SimpleIME와 무관하게, 게임 창에서 한/영 전환이 되지 않는다. 맞다면 SimpleIME를 꺼도 영문이 들어간다.
- 둘을 가르는 시험: MO2에서 SimpleIME만 끄고 같은 검색창에 한/영 키를 눌러 가며 쳐 보기. 로그의 `검색창: 조합 …` 줄이 생기는지를 봅니다.
- 가설 A가 맞을 때의 과제: 한글을 쓰는 사용자는 SimpleIME를 깔아 둔 경우가 많을 것이므로, 함께 쓸 방법(글자 입력칸이 열렸다고 게임에 알려 SimpleIME의 입력기를 켜고, 그 결과 글자를 화면으로 받아 오기)이 필요합니다. 붙여 넣기(Ctrl+V)는 Prisma UI가 키 입력으로 처리하므로 될 가능성이 있으나 확인하지 않았습니다.

### 4차 시험 결과 (2026-11-13, SimpleIME를 끄고)

MO2에서 SimpleIME만 끄고 같은 시험을 했습니다(이 실행에서 SimpleIME의 로그가 갱신되지 않은 것으로 꺼져 있었음을 확인). 사용자가 본 것: **한글이 들어감. 조합 중인 글자가 검색창 바로 아래 작은 상자에 보이면서 들어감.**

한글 입력:

- 로그에 `조합 'ㅋ'` → `'키'` → `'킷'` → `'스'`(이때 `입력값 '키'`) → … → `입력값 '키스톤', 결과 49개`가 남았습니다. 조합 상태 이벤트가 오고, 확정된 글자가 글자 입력으로 들어오며, 조합 중에도 검색 결과가 따라옵니다.
- **3차 시험의 가설 A가 맞았습니다.** SimpleIME를 끈 것 하나만 바꿨는데 조합이 시작됐습니다. SimpleIME가 켜져 있으면 그 모드의 창이 키보드 포커스를 쥐고 입력기를 꺼 두어, Prisma UI 화면에는 영문만 넘어옵니다. (3차 때 한/영 키를 눌렀는지는 로그에 남지 않아, 그 부분만은 사용자의 말에 기댑니다.)
- 통과 기준의 "한글 입력"은 SimpleIME가 없을 때 통과, 있을 때 실패입니다. 한글을 쓰는 사용자는 SimpleIME를 켜 둔 경우가 많을 것이므로 함께 쓰는 방법을 정해야 합니다(설계-현황 5장 35번).

측정(게임을 멈추고 연 상태, 타일 결함을 고친 뒤 처음으로 끝까지 돈 것):

| 측정 (화면 3840x2160) | 게임을 멈추고 엶(4차) | 게임을 돌린 채 엶(3차) |
| --- | --- | --- |
| 기준: 트리를 그리지 않을 때 | 60.6 FPS (16.5ms) | 60.6 FPS (16.5ms) |
| 기준: 점 몇 개만 바꿀 때 | +0.1ms | +1.1ms |
| 타일, 캔버스 3840x2160 | 평균 27.2 FPS, 가장 느린 1% 17.9. 그리는 시간 19.9ms | 평균 24.8 FPS, 가장 느린 1% 16.9. 그리는 시간 20.7ms |

### 이 프로토타입의 결론

"무엇을 확인하는가"의 세 질문에 대한 답입니다.

1. **노드 수천 개의 트리를 Canvas 2D로 끊기지 않게 움직일 수 있는가.** 화면이 1920x1080 정도면 됩니다. 3840x2160을 그대로 그리면 안 됩니다(평균 25~27 FPS). 캔버스를 1920x1080으로 그려 늘리면 평균 38~47 FPS입니다. Prisma UI에서는 그리는 시간이 게임의 프레임 시간에 그대로 더해지므로, 화면의 프레임이 곧 게임의 프레임입니다. 가만히 있을 때는 부담이 없습니다.
2. **3단 구성(바닥 타일, 덧그림, HTML 툴팁·검색)이 필요한가.** 필요합니다. 매 프레임 다 그리는 방식은 타일 방식보다 느렸습니다(1차: 25 대 31 FPS). 타일을 만드는 일은 프레임마다 시간 한도를 두고 나눠야 하고, 타일 수의 한도는 화면 크기에 맞춰야 합니다.
3. **검색이 입력을 따라오는가, 한글 입력이 되는가.** 검색은 5ms 안입니다. 한글은 Prisma UI의 `prismaIME_state` 이벤트를 받아 조합 글자를 직접 그려 주면 됩니다. SimpleIME가 켜져 있으면 안 됩니다.

Claude의 권고(결정 아님, 설계-현황 5장 34번): 캔버스의 내부 해상도는 세로 1080을 넘지 않게 하고, 트리 화면은 게임을 멈추고 여는 것을 기본으로 합니다. 절반 해상도의 선명함이 쓸 만한지는 사용자가 "해상도" 버튼으로 본 느낌을 들어야 합니다.

### 검수에서 고친 것 (2026-11-13)

네 번의 시험 동안 쌓인 변경을 검수해 8건을 고쳤습니다. 브라우저에서 흐름을 확인했고 다시 배치했습니다. 게임 안에서는 돌려 보지 않았습니다.

- 조합 중인지의 판정을 조합 글자나 후보가 실제로 있을 때로 좁혔습니다(조합이 끝난 뒤 Enter·Esc가 막힐 수 있던 것).

- 버려진 측정의 오류가 새 측정의 상태 글을 덮지 않습니다.
- 닫을 때 타일을 버립니다. 타일 한도(화면에 따라 160~200장)는 측정한 조건과 같게 그대로 두었습니다.
- 검색창 기록을 INI의 `LogSearchInput`으로 켜게 했습니다(기본 꺼짐).
- INI의 설명과 낡은 주석을 지금 동작에 맞췄습니다.
