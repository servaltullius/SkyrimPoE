# 프로토타입 2: 입력에 스킬 얹기 (사이클론 두 방식 비교 포함)

상태: 1차 시험 마침(2026-11-12). 두 방식 모두 강공격 입력으로 회전이 나오고 적이 맞음(사용자 관찰 + 로그). 사용자가 OAR 방식으로 확정(결정 48). 짧게 눌렀을 때의 처리는 남음. 짧게 끝난 채널링의 원인을 가리려고 입력 기록을 추가해 다시 배치함

## 무엇을 확인하는가

1. **입력을 가로채지 않고 강공격을 스킬로 바꿀 수 있는가.** 통합 설계서 6.2의 "채널링 = 강공격 버튼을 누르고 있는 동안"과 14장 2번(입력에 스킬 얹기)입니다.
2. **사이클론 모션의 두 방식을 같은 입력으로 구동했을 때 어느 쪽이 나은가.** 프로토타입 1에서 모션은 둘 다 됐고, 1A의 문제는 Animation Injector가 공격 버튼 입력을 가로채는 부분이었습니다. 그래서 입력은 이 DLL이 맡고, 모션만 두 방식으로 바꿔 가며 비교합니다(결정 22를 닫기 위한 시험).

## 어떻게 동작하는가

DLL 이름은 `PoEProtoSkillInput`입니다. 하는 일은 세 가지입니다.

- **버튼 상태를 읽습니다.** 입력 장치 관리자에 읽기 전용 싱크를 붙여 공격 버튼이 눌려 있는지만 봅니다. 입력 이벤트를 고치거나 지우지 않으므로 짧은 클릭의 일반 공격은 평소대로 나갑니다.
- **강공격이 시작되려는 순간을 받습니다.** 게임(또는 공격 모드)은 강공격을 시작할 때 플레이어에게 `attackPowerStart…` 같은 애니메이션 이벤트를 보냅니다. 이 DLL은 플레이어의 `NotifyAnimationGraph`에 훅을 걸어, 공격 버튼을 누르고 있는 상태에서 그 이벤트가 오면 게임에 넘기지 않고 채널링을 시작합니다. 어떤 키로 강공격을 내는 환경이든 "강공격이 시작되려 한다"는 지점은 같으므로, 입력 방식에 덜 묶입니다.
- **회전 모션을 켜고 끕니다.** 방식에 따라 다릅니다.

| | OAR 방식 (1B) | Animation Injector 방식 (1A) |
| --- | --- | --- |
| 시작 | 액터 값 `Variable09`를 1로 두고 `attackStop`으로 진행 중인 공격을 끊음 | 플레이어에게 `PoEProto_CycloneStart` 이벤트를 보냄 |
| 끝 | `Variable09`를 0으로 | `PoEProto_CycloneStop` 이벤트를 보냄(마무리 동작으로 넘어감) |
| 회전 중 이동 | 평소의 걷기·달리기 그대로, 클립만 회전 모션 | 애니메이션이 이동을 정함(클립의 전진 이동 + 이동 키로 방향 전환). 소스로 확인, 관찰로는 미확인 |
| 필요한 모드 | `[PoE Proto] 1B Cyclone - OAR` | `[PoE Proto] 1A Cyclone - Animation Injector` |

채널링 중에는 누르고 있는 버튼 때문에 공격이 다시 시작되지 않도록 공격 시작 이벤트를 막습니다. 버튼을 떼거나, 무기를 넣거나, 경직·사망·탑승 같은 상태가 되거나, 최대 시간(기본 60초)이 지나면 끝납니다.

안전 장치:

- 누르고 있는 버튼의 "눌려 있음" 이벤트가 0.5초 넘게 끊기면 뗀 것으로 봅니다. 창이 포커스를 잃어 뗌 이벤트가 오지 않아도 회전이 남지 않습니다. 이때 로그에 `[입력] … 뗀 것으로 처리함` 줄이 남습니다.
- 고른 모션 쪽의 DLL(`OpenAnimationReplacer.dll` 또는 `AnimationInjector.dll`)이 로드돼 있지 않으면 강공격을 가로채지 않고 그대로 통과시킵니다.
- 세이브를 불러오기 시작할 때 진행 중인 채널링을 끝냅니다.
- Animation Injector 방식에서는 시작 0.5초 뒤 `bAnimationDriven` 값을 한 번 읽어 로그에 남깁니다. 동작이 실제로 시작됐는지 보는 참고용이고, 이 값으로 채널링을 끊지는 않습니다.

시작 계기는 두 가지를 넣었습니다.

- **강공격 가로채기**(기본): 위에서 설명한 방식.
- **길게 누르기**: 오른손 공격 버튼을 0.3초 넘게 누르고 있으면 시작. 강공격이 공격 버튼의 길게 누름이 아닌 환경(전용 키, 우클릭 등)에서 쓸 대안입니다. 이 경우 누르는 순간 일반 공격이 먼저 시작됐다가 0.3초 뒤 회전으로 바뀝니다.

## 시험 방법

1. MO2를 새로 고치고 다음 세 모드를 켭니다.
   - `[PoE Proto] 1A Cyclone - Animation Injector` (XML이 바뀌었습니다. 이제 공격 버튼 입력을 잡지 않습니다)
   - `[PoE Proto] 1B Cyclone - OAR`
   - `[PoE Proto] 2 Skill Input` (새로 생긴 모드)
2. 게임을 완전히 다시 시작합니다.
3. 근접 무기를 꺼냅니다.
4. 짧게 클릭해 평소 일반 공격이 나가는지 봅니다.
5. 평소 강공격을 내던 방법 그대로 입력하고, 버튼을 누른 채로 있습니다. 강공격 대신 회전이 나와야 합니다. 누른 채 이동해 보고, 뗍니다.
6. **F10**을 누르면 방식이 바뀌고 화면 왼쪽 위에 지금 방식이 표시됩니다. 순서는 다음과 같습니다.
   - OAR + 강공격 가로채기 (처음 상태)
   - Animation Injector + 강공격 가로채기
   - OAR + 길게 누르기
   - Animation Injector + 길게 누르기
7. 5번에서 회전이 안 나오면 F10을 두 번 눌러 "길게 누르기"로 바꾼 뒤, 공격 버튼을 길게 눌러 봅니다.
8. 아래 기준을 방식별로 봅니다. 느낀 점만 말로 알려 주시면 됩니다. 로그는 Claude가 읽습니다.

F10이 다른 모드와 겹치면 `SKSE\Plugins\PoEProtoSkillInput.ini`의 `CycleKey`를 바꾸면 됩니다.

## 아직 모르는 것

실행으로 확인한 것은 없습니다. 아래는 이번 시험으로 가려질 항목입니다.

- 이 모드팩(MCO)에서 강공격이 시작될 때 실제로 어떤 이벤트가 오는지. DLL은 이름에 `attack`과 `power`가 있고 `start` 또는 `initiate`로 시작을 뜻하는 이벤트를 강공격 시작으로 봅니다. 맞지 않으면 로그에 남은 실제 이벤트 이름을 보고 고칩니다.
- 그 이벤트가 플레이어의 `NotifyAnimationGraph`를 거쳐 오는지. 거치지 않으면 "강공격 가로채기"는 동작하지 않고 "길게 누르기"만 됩니다.
- OAR 방식에서 `attackStop`이 진행 중인 MCO 공격을 끊고 이동 상태로 돌려보내는지.
- Animation Injector가 다른 DLL이 보낸 이벤트로 동작을 시작·종료하는지. 소스(커밋 `dc3c0b7`의 `core/PlayerHooks.cpp`, `runtime/ActionLinks.cpp`)로는 그렇게 읽히지만 실행해 보지 않았습니다.
- 누르고 있는 버튼의 "눌려 있음" 이벤트가 매 프레임 온다는 전제. 바닐라의 길게 눌러 강공격과 Animation Injector 소스가 이 반복 이벤트에 기대고 있어 그렇다고 보았지만, 이 DLL에서 실행으로 확인하지는 않았습니다. 전제가 틀리면 회전이 0.5초 만에 끝나고 로그에 `[입력]` 줄이 남습니다.
- 강공격 이벤트를 받지 않고 버렸을 때 게임이나 MCO가 어떻게 반응하는지(같은 이벤트를 계속 다시 보내는지 등).
- 바닐라 공격 환경과 BFCO 환경, SE 1.5.97에서의 동작. 이 컴퓨터의 AE 1.6.1170 + MCO에서만 시험합니다.

## 알아 둘 점

- 회전 모션과 타격은 프로토타입 1과 같은 빌려 온 클립에서 나옵니다(`../01-cyclone-motion/README.md` 참고).
- OAR 방식의 `Variable09`는 세이브에 남는 값입니다. DLL은 세이브를 불러온 직후 이 값을 0으로 되돌립니다. 그래서 이 DLL이 켜져 있는 동안에는 콘솔로 `player.setav variable09 1`을 해 둔 상태가 불러오기를 넘어 유지되지 않습니다.
- 제품에서는 액터 값 대신 OAR의 플러그인 조건 API로 "채널링 중" 조건을 직접 제공하는 편이 낫습니다(세이브에 남지 않음). 이 프로토타입에서는 1B의 설정을 그대로 쓰려고 액터 값을 썼습니다. Claude의 제안이며 정해진 것은 아닙니다.
- 강공격을 가로챘는데 그 사이에 버튼을 떼면, 강공격도 회전도 나오지 않고 지나갑니다.
- 오른손에 근접 무기가 있을 때만 동작합니다. 맨손, 활, 지팡이, 주문은 대상이 아닙니다.
- 로그 파일: `Documents\My Games\Skyrim Special Edition\SKSE\PoEProtoSkillInput.log`. `LogEvents = true`인 동안 공격 관련 이벤트와 처리 결과가 한 줄씩 남습니다.

## 파일

- `src/Core/Config.*`: INI 읽기(게임 타입에 기대지 않음, 테스트 대상)
- `src/Core/EventNames.*`: 애니메이션 이벤트 이름으로 공격 시작·강공격 시작을 가려내는 규칙(테스트 대상)
- `src/Runtime/Channel.*`: 채널링 한 번의 시작부터 끝까지
- `src/Runtime/Hooks.*`: 입력 싱크, `NotifyAnimationGraph` 훅, `Update` 훅
- `src/main.cpp`: 플러그인 진입점, 로그, SKSE 메시지
- `dist/SKSE/Plugins/PoEProtoSkillInput.ini`: 배포되는 설정 파일
- `tests/ConfigTests.cpp`, `tests/EventNamesTests.cpp`: 설정 읽기와 이벤트 이름 판별 테스트(빌드 때 실행, 2개 통과)
- `CMakeLists.txt`, `CMakePresets.json`, `vcpkg.json`, `build.bat`

사용자 관찰: **"둘 다 회전 잘되고 타격도 잘 되었음."** OAR 방식과 Animation Injector 방식 모두, 강공격 입력으로 회전이 나오고 회전에 닿은 적이 맞았습니다. 입력을 가로채지 않고 강공격을 채널링으로 바꾸는 방식이 두 모션 방식 모두에서 성립했습니다(이 컴퓨터의 AE 1.6.1170 + MCO 환경).

이 결과를 보고 사용자가 **사이클론 모션을 OAR 방식으로 확정했습니다(설계-현황 결정 48).** Animation Injector 방식은 사이클론에 쓰지 않습니다. 이 DLL의 `Motion = injector`와 1A 모드는 비교 기록으로 남겨 두며, 이후 시험은 OAR 방식만 봅니다.

회전 중 이동, 떼었을 때의 모습, 짧게 끝난 구간에서 누른 버튼은 아직 듣지 못했습니다. 아래는 로그가 말해 주는 것입니다.

로그로 확인된 것:

- 바꾼 1A XML이 읽혔습니다. `AnimationInjector.log`: `cyclone.xml: validated`, "액션 2개 로드", 상태 7700·7701 주입.
- DLL이 로드됐고 훅과 입력 싱크가 설치됐습니다. Open Animation Replacer와 Animation Injector 모두 "로드됨"으로 감지됐습니다.
- **이 모드팩에서 강공격 시작 이벤트는 `attackPowerStartInPlace`입니다.** 공격 버튼을 누르면 `attackStart`가 오고, 누르고 있으면 약 0.25초 뒤에 이 이벤트가 옵니다. 플레이어의 `NotifyAnimationGraph`를 거쳐 오며, DLL이 받아서 채널링으로 바꿨습니다("강공격을 채널링으로 바꿈").
- 짧은 클릭의 일반 공격은 `attackStart` → `attackRelease`로 그대로 통과했습니다(수십 회).
- OAR 방식: 채널링이 16번 시작됐습니다. `attackStop`은 15번 받아들여졌고 1번 거부됐습니다. 길게 이어진 것은 2.63초와 3.40초이고, 둘 다 "버튼을 뗌"으로 끝났습니다.
- Animation Injector 방식: 2번 시작됐습니다(강공격 가로채기 1, 길게 누르기 1). `PoEProto_CycloneStart`가 받아들여졌고, 0.5초 뒤 `bAnimationDriven`이 켜져 있었습니다. 다른 DLL이 보낸 이벤트로 동작이 시작된다는 것이 실행으로 확인된 셈입니다(화면 확인은 아님). 각각 0.52초, 0.86초에 "버튼을 뗌"으로 끝났습니다.
- "눌려 있음 이벤트가 끊김" 줄은 한 번도 없었습니다. 3.4초 동안 누르고 있어도 끊기지 않았으므로, 누르고 있는 버튼의 이벤트가 계속 온다는 전제는 맞았습니다.
- DLL 로그에 오류·경고 없음. OAR 로그에 이 서브모드에 대한 경고 없음. 크래시 로그 없음.

설명되지 않은 것:

- **아주 짧게 끝난 채널링이 여러 번 있습니다.** OAR + 강공격 가로채기 방식에서 16:04:45~16:04:54 사이에 0.02~0.99초짜리가 14번 찍혔습니다. 대부분 앞에 `attackStart` 없이 `attackPowerStartInPlace`만 왔고, 곧바로 "버튼을 뗌"으로 끝났습니다.
  - 가설 A: `attackStart` 없이 곧바로 강공격을 내는 다른 버튼(예: 우클릭)을 짧게 여러 번 누른 것. 이 경우 DLL은 설계대로 동작한 것이고, "강공격을 짧게 누르면 강공격은 사라지고 회전은 한순간 스치고 끝난다"는 설계 문제가 드러난 것입니다.
  - 가설 B: 버튼을 누르고 있는데도 뗌 이벤트가 들어온 것(다른 모드가 입력을 합성하는 경우 등).
  - 이 로그에는 어떤 버튼이 언제 눌리고 떼였는지가 없어 가를 수 없습니다. 그래서 시험 직후 DLL에 버튼 누름·뗌 기록(`[입력] 오른손 공격 버튼 누름/뗌`)과 채널링이 어느 버튼에 묶였는지를 로그에 추가했습니다. 다음 시험에서 가려집니다.
- OAR + 길게 누르기 방식(16:05:03 이후 약 14초)에서는 채널링이 한 번도 시작되지 않았습니다. 그동안 `attackStart`/`attackRelease` 쌍이 약 0.16초 간격으로 반복됐고 강공격 이벤트는 없었습니다. 빠르게 연타한 것이라면 정상이고, 누르고 있었던 것이라면 가설 B와 같은 원인입니다.
- 첫 채널링(2.63초) 도중, 시작 2.0초 뒤에 `attackPowerStartInPlace`가 한 번 더 와서 막혔습니다. 게임이 누르고 있는 동안 강공격을 다시 시도한 것인지, 다른 버튼을 누른 것인지 알 수 없습니다.

이 시험으로 드러난 설계 문제(Claude의 판단, 미결정):

- 강공격 입력을 짧게 눌렀다 떼면 강공격은 삼켜지고 회전은 거의 보이지 않습니다. 최소 지속 시간(예: 한 바퀴)을 두거나, 일정 시간 안에 떼면 원래의 강공격을 내보내는 처리가 필요합니다. 어느 쪽으로 할지는 정하지 않았습니다.
