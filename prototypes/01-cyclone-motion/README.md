# 프로토타입 1: 사이클론 모션

상태: 2차 시험까지 마침 (2026-11-12). 회전 중 이동(기준 1번)은 1A와 1B 모두 통과. 1A는 4번 기준(짧게 누르면 평소 공격) 실패. 아래 "결과" 참고

**2026-11-12 변경:** 2차 시험 뒤 1A의 XML을 바꿨습니다. 이제 1A는 공격 버튼 입력을 받지 않고, 프로토타입 2의 DLL(`PoEProtoSkillInput`)이 보내는 이벤트로 시작하고 끝납니다. 그래서 1A만 켜서는 아무 일도 일어나지 않습니다. 두 방식의 비교 시험은 `../02-skill-input/README.md`의 절차로 이어집니다. 아래의 "켜는 법"과 "시험 방법"은 1·2차 시험 때의 내용입니다(1B를 콘솔로 켜는 방법은 지금도 그대로 됩니다).

## 무엇을 확인하는가

사이클론은 "버튼을 누르고 있는 동안 회전하면서 자유롭게 움직이고, 떼면 바로 멈춘다"가 성립해야 합니다.
네메시스나 판도라 패치 없이 이것을 만드는 방법 두 가지를 같은 조건에서 비교합니다(통합 설계서 6.7, 14장 1번).

| | 1A: Animation Injector | 1B: OAR 이동 클립 교체 |
| --- | --- | --- |
| 원리 | 새 동작을 행동 그래프에 끼워 넣고 반복 재생 | 걷기·달리기·대기 클립을 조건이 참인 동안 회전 모션으로 바꿈 |
| 켜는 법 | 무기를 꺼내고 공격 버튼을 길게 누름 | 콘솔에서 `player.setav variable09 1` |
| 끄는 법 | 버튼을 뗌 | 콘솔에서 `player.setav variable09 0` |
| 이 시험에 DLL이 필요한가 | 아니오 | 아니오 |
| 예상 | 입력 처리는 깔끔하지만 회전 중 이동이 안 될 가능성 | 이동은 그대로 되지만 시작·끝 연출과 입력은 따로 만들어야 함 |

1B를 콘솔로 켜고 끄는 것은 모션만 먼저 보기 위해서입니다. 실제로는 우리 DLL이 버튼 입력에 맞춰 같은 값을 바꾸게 됩니다(프로토타입 2).

## 시험 방법

1. MO2를 새로 고치면 왼쪽 목록 맨 아래에 다음 두 모드가 꺼진 채로 보입니다.
   - `[PoE Proto] 1A Cyclone - Animation Injector`
   - `[PoE Proto] 1B Cyclone - OAR`
2. 둘 다 켭니다. 서로 다른 방법으로 켜지므로 같이 켜 두어도 됩니다.
3. 게임을 완전히 다시 시작합니다. Animation Injector는 게임을 시작할 때만 XML을 읽습니다.
4. 무기(한손 또는 양손)를 꺼냅니다.
5. 1A: 공격 버튼을 길게 누르고, 누른 채로 이동 키와 마우스를 움직여 봅니다. 뗍니다. 짧게도 눌러 봅니다.
6. 1B: 콘솔(`~`)을 열어 `player.setav variable09 1`을 입력하고 닫은 뒤 움직여 봅니다. 다시 콘솔에서 `player.setav variable09 0`.
7. 위 표의 기준을 하나씩 봅니다.

시험이 끝나면 느낀 점만 말로 알려 주시면 됩니다. 로그는 Claude가 직접 읽습니다.

- `Documents\My Games\Skyrim Special Edition\SKSE\AnimationInjector.log`
- `Documents\My Games\Skyrim Special Edition\SKSE\OpenAnimationReplacer.log`

## 알아 둘 점

- **회전 모션은 빌려 온 것입니다.** 모드팩에 있는 "뉴 특대검 무브셋"의 반복 회전 공격(`mco_powerattackloop1.hkx`)을 씁니다(2026-11-12, 사용자 제안으로 바닐라 임시 모션에서 교체). 다른 사람의 에셋이므로 이 컴퓨터의 시험에만 쓰고 배포물에는 넣지 않습니다.
- 이 클립에는 주석이 들어 있습니다: 휘두르는 소리(`weaponswing`), 타격(`HitFrame`), Precision의 무기 충돌(`Collision_Add … DamageMult(0.8) scale(2)`), Payload Interpreter의 공격 속도 지정, 그리고 AMR의 전진 이동(`animmotion 0 20 0` ~ `0 80 0`). 그래서 시험 중에 소리가 나거나, 주변 적이 실제로 맞거나, 캐릭터가 조금씩 앞으로 밀릴 수 있습니다. 어느 방식에서 어떤 것이 일어나는지도 알려 주세요. 타격이 실제로 들어간다면 사이클론의 다단 타격을 따로 구현하지 않아도 될 가능성이 있습니다.
- 원래 이 무브셋에서는 특대검을 들고 강공격을 누르고 있을 때 나오는 동작입니다. 그때의 느낌(회전 중 이동이 되는지)과 비교해 주시면 기준이 됩니다.
- 한손 무기를 든 채로도 같은 양손 회전 모션이 나옵니다.
- 1A가 켜져 있는 동안에는 무기를 든 상태에서 공격 버튼을 길게 눌러 내던 강공격이 나가지 않습니다. 이 입력을 사이클론이 가져가기 때문입니다.
- 1B는 1인칭 클립을 바꾸지 않습니다. 1인칭에서는 팔 모양이 그대로일 것입니다.
- 이 모드팩에는 Animation Injector용 동작 모드가 아직 하나도 없어서(로그에 "액션 0개"), 1A가 첫 사례입니다.
- 1B의 우선순위는 2,000,000,000입니다. 이보다 높은 서브모드 가운데 같은 클립을 건드리는 것은 Disable Turn Animation(제자리 돌기)과 특정 NPC용 설정뿐이라 플레이어의 걷기·달리기에는 영향이 없습니다.


## 결과

### 1차 시험 (2026-11-12 14:24~14:29)

- **1A는 시험되지 않았습니다.** Animation Injector가 XML을 통째로 무시했습니다. 로그: `/AnimationSet/Action/Exit: 현재 런타임은 이 위치에 끝 기준 시각만 지원합니다 — entire file skipped`, 이어서 "액션 0개 로드". 원인은 Claude가 마무리 동작에 `<Exit at="0.05">`라고 쓴 것입니다. `Exit`의 `at`은 `end`, `end-N`, `event:이름`만 받습니다. 그래서 이 시험에서 공격 버튼을 길게 눌렀을 때 나온 것은 평소의 강공격입니다.
- 고친 것: 마무리 동작을 `<MoveCancel at="0.1">` + `<Exit blend="0.2">`로 바꾸고, 마무리 클립을 특대검 무브셋의 마무리 공격(`mco_powerattackoutro1.hkx`)으로 따로 두었습니다. 고친 파일은 Animation Injector의 파서 소스(`declarations/XmlV2.cpp`, `Cards.cpp` 등)와 요소·속성 하나씩 대조했습니다. 게임에서 읽히는지는 다음 시험의 로그로 확인합니다.
- **1B는 핵심 기준을 통과했습니다.** 사용자 관찰: "콘솔은 움직이고 적한테 공격도 되었음". 즉 값을 1로 두면 회전하는 채로 이동할 수 있었고, 회전에 닿은 적이 실제로 맞았습니다. 기준 1번(회전 중 이동) 통과.
  - 타격이 들어간 것은 클립에 든 주석 덕분입니다(`HitFrame`, Precision의 `Collision_Add`). 이동 상태에서 재생되는 클립인데도 타격이 처리됐습니다. 어느 주석이 타격을 만들었는지(엔진의 `HitFrame`인지 Precision의 충돌인지)는 가려내지 않았습니다. Precision이 없는 환경에서도 맞는지는 따로 확인해야 합니다.
  - 아직 확인하지 못한 기준: 2번(끄면 바로 멈추는지), 3번(시점 회전), 5번(점프·질주·방어), 6번(반복), 7번(1인칭). 저절로 앞으로 밀리는지도 미확인.
- OAR 로그에 이 서브모드에 대한 오류나 경고는 없습니다. OAR은 서브모드별 적용 여부를 로그에 남기지 않습니다.
- 크래시 로그는 새로 생기지 않았습니다.

### 2차 시험 (2026-11-12 15:10~15:14)

- **고친 XML은 게임에서 읽혔습니다.** `AnimationInjector.log`: `cyclone.xml: validated`, "액션 3개 로드", `CycloneLoop`와 `CycloneEnd`가 3인칭 전신 그래프에 상태 7700·7701로 들어감, 클립 2개 프리로드 실패 0. 오류와 경고 없음(기준 8번 통과).
- **1A는 기준 4번에서 실패했습니다.** 사용자 관찰: "인젝터는 대신에 클릭으로 일반공격이 안되는듯". 1A를 켜 둔 상태에서 마우스를 짧게 클릭해도 평소의 일반 공격이 나가지 않았습니다.
- **1A도 기준 1번을 통과했습니다.** 사용자 관찰: "1a도 회전 나왔고 이동키로 이동 되었음". 공격 버튼을 길게 누르면 회전이 나오고, 회전하는 채로 이동 키로 움직일 수 있었습니다. 시험 전에 Claude가 한 예상(1A는 회전 중 이동이 안 될 것)은 틀렸습니다.
  - 이 이동이 어떤 성격인지는 가려내지 않았습니다. 안내서에 따르면 `<Rotate>` 구간에서는 이동 키를 누르고 있으면 캐릭터가 그 방향으로 돌고, 이 클립에는 앞으로 나아가는 이동 주석(AMR `animmotion`)이 있습니다. 그래서 "클립이 앞으로 밀고 이동 키로 방향을 트는" 이동일 수 있습니다(추정). 그렇다면 이동 속도가 캐릭터의 이동 속도가 아니라 클립에 묶입니다. 가르는 관찰: 이동 키를 안 누르면 제자리에서 도는지 저절로 나아가는지, 뒤·옆으로도 가는지, 속도가 평소 달리기와 같은지.
  - 1B의 이동은 평소의 걷기·달리기 그대로이고 클립만 바뀐 것이므로, 이동 속도 변화가 그대로 반영됩니다.
- 로그는 `bDebug = false`라 동작 실행을 남기지 않습니다.

일반 공격이 안 나가는 이유에 대해 확인한 것과 남은 가설:

- 확인(소스, 커밋 `dc3c0b7`의 `core/InputDispatchHook.cpp`, `runtime/InputSink.cpp`, `core/GameInputReplay.cpp`, `runtime/PressKinds.cpp`): 공격 버튼에 `press="hold"` 시작이 걸려 있으면, Animation Injector는 누름과 뗌 이벤트를 `PlayerControls`로 가는 목록에서 빼 둡니다. 0.2초 안에 떼면 그다음 틱에 가짜 누름(값 1, 누른 시간 0)과 가짜 뗌(값 0, 누른 시간 0.1 고정)을 **한 번에 연달아** 입력 관리자로 다시 보냅니다. 핸들러를 직접 부르지는 않습니다. 즉 안내서의 "늦게 게임으로 돌아간다"는 실제로는 "버튼을 뗀 뒤에, 누름과 뗌이 같은 순간에 붙어서 돌아간다"입니다.
- 확인(환경): 이 모드팩의 공격은 바닐라가 아닙니다. 오늘 세션의 `skse64.log`에서 `MCO.dll`(`MCO Universal Support`)이 로드됐고, 공격 행동은 `Attack - MCO - TKL`입니다. MCO.dll이 공격 입력을 어떻게 처리하는지는 확인하지 못했습니다.
  - 정정: 처음에는 여기에 "For Honor Power Attack이 입력을 직접 읽는다"고 적었는데 틀렸습니다. 근거로 삼은 `ForHonorPowerAttack.log`는 2026-09-15의 것이었고, 오늘 세션에는 `ForHonorPowerAttack.dll`과 `OneClickPowerAttack.dll`이 로드되지 않았습니다(MO2의 `For Honor Power Attack` 모드 폴더에는 `meta.ini`만 있음).
- 가설 A(근거: 소스로 확인한 합성 입력의 모양뿐, 직접 증거 없음): 공격 처리 쪽이 가짜 누름과 뗌이 같은 순간에 붙어서 오는 입력을 공격으로 인정하지 않는다.
- 가설 B(근거 약함): 가짜 입력 자체가 나가지 않았다(메뉴·콘솔로 대기가 버려졌거나, 읽지 못한 `ActionLinks` 쪽에서 입력을 가져감).
- 두 가설을 가르는 증거: `AnimationInjector.ini`의 `bDebug = true`로 다시 시험했을 때 `[Press] late game press 'rightAttack' tap` 줄이 찍히면 A, 안 찍히면 B. 바닐라 공격 환경에서 같은 XML로 일반 공격이 나가는지도 A를 가릅니다. 아직 하지 않았습니다.
- 어느 가설이든 달라지지 않는 것: 이 방식에서는 모든 일반 공격이 "버튼을 뗀 뒤"에야 나가고, 공격 모드가 받는 것은 실제 입력이 아니라 합성된 입력입니다. 일반 공격의 반응이 늦어지고, 공격 입력을 손대는 다른 모드와 맞물릴 위험이 구조적으로 있습니다. 공격 버튼을 Animation Injector의 입력 가로채기에 맡기는 것은 공개 배포용으로 권하기 어렵습니다(Claude의 판단).
- Animation Injector에는 입력을 건드리지 않고 애니메이션 이벤트로 동작을 시작하는 길(`<Start event="…">`)이 따로 있습니다. 우리 DLL이 이벤트를 보내 동작을 시작하게 하면 위 문제는 생기지 않습니다. 시험하지 않았습니다.
