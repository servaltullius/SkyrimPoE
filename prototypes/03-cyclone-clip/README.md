# 프로토타입 3: 사이클론 회전 모션 직접 만들기

상태: 초안이 게임에서 재생됐고 사용자 평가는 "쓸 만함"(2026-11-12 1차 시험). 통과 기준 두 가지 모두 통과. 타격 비교 시험 결과, 만든 클립도 제자리에서는 맞음. **이동하면 어느 클립이든 맞지 않고 모션이 끊김**(클립이 아니라 방식의 문제, 고칠 방향은 제안 단계). 한손 무기·세부 다듬기는 남음

## 무엇을 확인하는가

사이클론의 회전 모션을 우리가 직접 만들 수 있는가(통합 설계서 6.7의 [미정] 항목). 지금까지는 다른 모드의 클립을 빌려 이 컴퓨터에서만 시험했습니다. 직접 만들어야 하는 이유는 세 가지입니다.

- 빌린 클립은 배포물에 넣을 수 없습니다.
- 타격 주기를 우리가 정하려면(설계서: 무기 공격 속도의 300%) 클립의 길이와 주석을 우리가 쥐고 있어야 합니다.
- 빌린 클립에는 앞으로 밀려 나가는 이동 주석이 있습니다. OAR 방식은 평소의 이동을 쓰므로 없어야 맞습니다.

통과 기준은 두 가지입니다.

1. 만든 HKX가 게임에서 재생된다.
2. 사용자가 보기에 "임시로 쓸 만하다" 이상이다.

## PoE 사이클론 조사 (2026-11-12)

PoE의 파일은 뜯어 보지 않았습니다(결정 27·28의 "아이디어를 가지고 자체 구현"). 공개된 데이터와 영상의 화면만 봤습니다.

- 규칙(기준 PoB 3.29의 `Data/Skills/act_dex.lua`, poedb의 Cyclone 항목으로 대조): 채널링하는 동안 목표 지점으로 이동하면서 회전하며 주변을 계속 공격함. 공격 속도는 기본의 300%, 채널링 중 이동 속도는 20~30% 감소, 기본 반경 16(1.6미터)이고 근접 공격 거리가 늘면 범위가 커짐, 밀려나지 않음. 쓸 수 있는 무기는 한손·양손 근접 무기와 맨손(활·완드 제외).
- 한 바퀴에 몇 번 맞는지는 출처가 엇갈립니다(한 번이라는 설명과 두 번이라는 설명이 모두 있음). 직접 확인하지 못했습니다. poewiki는 봇 차단으로 열지 못했습니다.
- 모습(유튜브의 공식 스킬 효과 영상 두 편을 브라우저에서 멈춰 놓고 화면만 봄. 영상은 받지 않음): 카메라가 멀고 캐릭터가 작으며 이펙트가 몸을 덮습니다. 읽히는 것은 "몸은 곧게 선 채 제자리에서 돌고, 무기가 가슴~허리 높이에서 몸 둘레에 수평 원반을 그린다"는 실루엣까지입니다. 팔다리의 세부 자세는 읽히지 않았습니다.
- 여기서 얻은 것: PoE에서 사이클론을 사이클론답게 보이게 하는 것은 세부 자세보다 **회전 속도와 무기가 그리는 원반(궤적 이펙트)**입니다. 우리 쪽에서도 자세를 다듬는 것보다 무기 궤적 이펙트가 인상에 더 크게 작용할 가능성이 큽니다(Claude의 판단).

## 만든 방법

같은 사용자의 다른 프로젝트(`G:\skyrim project\스카이림 모션 작업`)가 쓰는 방식을 따랐습니다. 자세를 스크립트로 계산해 XML로 쓰고, 변환기로 게임용 HKX로 바꿉니다.

1. 바닐라 양손 대기 자세의 첫 프레임을 바탕으로 삼습니다(손가락이 손잡이를 쥔 모양과 뼈 길이를 얻기 위함).
2. 축발(왼발)을 몸 바로 아래에 두고 무릎을 굽혀 자세를 낮춥니다. 반대쪽 다리는 뒤로 뻗어 땅에서 띄웁니다.
3. 가슴을 무기 쪽으로 틀고, 두 팔을 가슴 앞으로 뻗어 무기를 수평으로 듭니다. 무기는 회전 방향의 뒤쪽으로 끌려옵니다.
4. 상체를 무기 반대쪽으로 기울이고, 머리는 몸이 나아가는 쪽을 보게 합니다.
5. 축발이 캐릭터의 세로축 위에 오도록 옮긴 뒤 몸 전체를 한 바퀴 돌립니다. 축발은 제자리에서 돌기만 하고 뒷발은 떠 있으므로 발이 땅을 미끄러지지 않습니다.
6. 한 바퀴 동안 골반이 두 번 가볍게 오르내립니다.

한 바퀴는 18프레임(0.6초)이고 위에서 볼 때 반시계 방향입니다. 지금 쓰던 빌린 클립과 같은 길이로 맞췄습니다. 자세의 수치는 `gen_cyclone.py`의 `Design`에 모여 있어 하나씩 바꿔 볼 수 있습니다.

참고한 것과 가져온 것:

- 빌린 클립은 구조만 분석했습니다(0.6초에 한 바퀴, 몸통 중심 뼈가 통째로 돎, 낮은 자세, 두 손으로 수평). 자세 데이터는 가져오지 않았고, 위의 수치는 전부 새로 정했습니다. "한 발을 축으로 삼고 다른 다리를 띄운다"는 발상은 빌린 클립을 그려 보고 얻은 것입니다.
- 주석은 게임 표준 이벤트(`weaponSwing`, `HitFrame`)와 Precision이 읽는 충돌 주석(`Collision_*`)을 넣었습니다. 충돌 주석의 설정값(`DamageMult(0.8)`, `scale(2)`, `NoRecoil`)은 빌린 클립에서 타격이 잘 됐던 값을 그대로 썼습니다. 앞으로 밀려 나가는 이동 주석(`animmotion`)과 Payload Interpreter 주석은 넣지 않았습니다.

## 다시 만들기

```bash
python gen_cyclone.py --skeleton "<skeleton.xml>" --base "<2hm_idle.xml>" --out out/cyclone_pose.xml
```

```bash
"<hkxc.exe>" convert -i out/cyclone_pose.xml -o out/cyclone_pose.hkx -v amd64
```

```bash
python preview.py out/cyclone_pose.hkx out/preview.png --motion-gen "<motion_gen 폴더>" --frames 0 --views "front,right,back,3/4,top"
```

```bash
python ../01-cyclone-motion/build_proto1.py --only 1b --clip out/cyclone_pose.hkx --deploy "G:\TAKEALOOK\mods"
```

기본은 정지 자세(`--mode static`)입니다. 회전과 타격 주석을 클립에 굽는 처음 방식은 `--mode spin`으로 남아 있습니다.

주석 배치는 `--annotations zero|shifted|shifted-prehit`로 고릅니다(기본 `shifted-prehit`). 비교용으로 여러 클립을 한 모드에 넣으려면 `build_proto1.py`에 `--variant-clip`을 클립마다 붙입니다. `--clip`이 1번, `--variant-clip`이 차례로 2번, 3번이 되고, DLL의 `ClipVariants`를 그 수에 맞춥니다.

- `skeleton.xml`, `2hm_idle.xml`: 바닐라 `Skyrim - Animations.bsa`의 스켈레톤과 `2hm_idle.hkx`를 hkxc로 XML로 바꾼 것. 이번에는 `G:\skyrim project\스카이림 모션 작업\motion_gen\data\`의 것을 읽었습니다. 바닐라 에셋이라 이 저장소에는 넣지 않습니다.
- `hkxc.exe`: serde-hkx의 변환기(SARDONYX, Apache-2.0 또는 MIT). 이번에는 `G:\skyrim project\스카이림 모션 작업\HKX_Edit\HKX_Edit\tools\hkxc.exe`를 썼습니다. `-v amd64`가 SE·AE용(64비트)입니다.
- `--motion-gen`: 미리보기는 그 프로젝트의 `qa_render.py`와 `skin.py`(스킨 메시 렌더)를 불러 씁니다. 읽기만 합니다.
- `gen_cyclone.py`는 만든 뒤 수치 점검을 합니다(반복 고리가 닫히는지, 축발이 세로축에서 벗어나지 않는지, 발 높이가 일정한지, 무기가 수평인지, 왼손이 손잡이에 닿는지, 팔다리가 다 펴지지 않았는지). 문제가 있으면 종료 코드 2로 끝납니다.

1. MO2에서 `[PoE Proto] 1B Cyclone - OAR`과 `[PoE Proto] 2 Skill Input`이 켜져 있는지 확인합니다(1A는 꺼도 됩니다).

3. 봐 주실 것:

   - 보기에 어떤가: 자세, 속도, 무기 높이, 어색한 곳
   - 적이 맞는가(빌린 클립 때와 비교)

   - 한손 무기를 들었을 때의 모습(지금은 한손 무기에도 같은 양손 자세가 나옵니다)

## 아직 모르는 것

- 이 형식(압축하지 않은 인터리브 애니메이션)의 HKX가 OAR의 이동 클립 자리에서 재생되는지. 같은 형식으로 만든 다른 프로젝트의 클립은 게임에서 쓰이고 있지만, 이 클립과 이 자리로는 처음입니다.
- 이동 상태에서 재생되는 클립의 `HitFrame`과 Precision 충돌 주석 가운데 무엇이 타격을 만드는지. 빌린 클립에서도 가리지 못했습니다. Precision이 없는 환경에서 맞는지도 미확인입니다.
- 게임 안에서의 모습. 미리보기 그림은 여자 기본 몸에 임의의 칼을 그린 것이라 실제 장비·체형과 다릅니다. 움직이는 모습은 그림으로 확인하지 못했습니다(정지 자세 네 장만 봄).
- 걷기·달리기·대기 클립이 서로 섞이는 순간(출발·정지)에 회전이 튀어 보이는지.

### 타격이 안 되는 원인: 확인한 것과 가설 (2026-11-12, 미확정)

확인한 것:

- 두 클립 모두 주석이 같은 자리(첫 번째 주석 트랙)에 들어 있습니다. 형식은 다릅니다(빌린 것은 스플라인 압축, 만든 것은 비압축). 같은 비압축 형식으로 만든 다른 프로젝트의 공격 클립은 게임에서 타격이 됩니다.
- Precision의 소스(`ersh1/Precision`의 `PrecisionHandler.cpp`, 설치본은 2.0.4이고 읽은 것은 저장소의 최신본이라 다를 수 있음)에서 주석의 처리는 이렇습니다.
  - `Collision_AttackStart`가 와야 그 뒤의 `Collision_Add`가 받아들여집니다.
  - `Collision_AttackStart`가 오지 않았으면 `weaponSwing`이나 `preHitFrame`이 기본 충돌을 만듭니다. 공격 상태가 아니어도 무기를 들고 있으면 기본 정의가 쓰입니다.
  - `Collision_AttackEnd`, `attackStop`, `staggerStart`는 충돌을 모두 지우고 시작 표시도 되돌립니다.
- 즉 소스대로라면 만든 클립의 주석으로도 충돌이 생겨야 합니다. 소스만으로는 원인이 설명되지 않습니다.
- 두 클립의 주석에서 다른 점은 둘입니다. 만든 클립은 `Collision_AttackStart`가 정확히 0초에 있고(빌린 것은 0.10초), `preHitFrame`이 없습니다(빌린 것은 0.03초에 있음).

가설:

- A. 0초의 주석은 재생이 시작되거나 반복될 때 놓친다. 그래서 `Collision_AttackStart`가 오지 않는다. (다만 그렇더라도 소스상으로는 `weaponSwing`이 기본 충돌을 만들어야 하므로 이것만으로는 부족합니다.)
- B. `preHitFrame`이 있어야 타격이 처리된다.
- C. 주석과 무관하게 자세의 차이(무기의 높이·거리·움직임) 때문에 충돌이 적에 닿지 않는다.
- D. 실제로는 맞았는데 눈에 띄지 않았다. 관찰이 "안 되는 것 같았다"였고, 적중을 세는 수단이 없었습니다.

가르는 방법(다음 시험, 준비해 둠):

- DLL이 플레이어의 적중을 로그에 남기고 채널링마다 횟수를 셉니다(`[타격] …`, `[채널링] 끝 … 적중 N회`).
- 1B 모드에 클립 네 가지를 넣었습니다. 게임 안에서 F10으로 바꿉니다(화면에 "회전 클립 n/4" 표시).

| 번호 | 클립 | 무엇을 가르는가 |
| --- | --- | --- |
| 1 | 만든 클립, 주석은 1차 시험 그대로(시작 표시가 0초) | 적중 0회면 "안 맞음"이 확인됨. 맞으면 가설 D |
| 2 | 만든 클립, 시작 표시를 0초에서 뗌 | 1번과 달리 맞으면 가설 A |
| 3 | 만든 클립, 2번에 `preHitFrame`을 더함 | 2번은 안 맞고 3번만 맞으면 가설 B |
| 4 | 빌린 클립(맞았던 것) | 기준. 이것만 맞으면 가설 C(자세) |

처음 번호는 3번입니다(`ClipVariant = 3`). 생성기의 기본 주석 배치도 3번과 같은 `shifted-prehit`으로 바꿨습니다.

| 2 | 만든 클립, 시작 표시를 뗌 | 9회(14.6초), 26회(9.7초), 6회(2.0초) |
| 3 | 만든 클립, + preHitFrame | 8회(9.5초), 25회(11.5초), 4회(2.4초), 6회(2.9초) |
| 4 | 빌린 클립 | 20회(7.2초), 0회(6.1초), 4회(1.5초), 4회(2.7초) |

확정된 것:

- **만든 클립은 맞습니다.** 네 가지 모두 제자리에서는 적중이 기록됐습니다. 1번(1차 시험과 같은 클립)도 맞으므로, 1차 시험에서 "안 맞는 것 같았던" 것은 클립의 주석 때문이 아닙니다. 가설 A(0초 주석)와 B(preHitFrame)는 기각입니다.
- **이동하면 맞지 않습니다. 빌린 클립도 마찬가지입니다.** 적중 0회였던 긴 채널링이 1번과 4번에 하나씩 있습니다. 즉 클립의 문제가 아니라 "이동 클립 자리에 재생되는 회전 클립의 주석으로 타격을 낸다"는 방식의 문제입니다.
- 이동하면 회전 모션이 끊깁니다(사용자 관찰).

원인(가설, 미확정):

- 이동 중에는 여러 방향·속도의 이동 클립이 동시에 섞여 재생됩니다. 우리는 그 클립들을 전부 같은 회전 클립으로 바꿨으므로, 회전 클립 여러 벌이 서로 다른 시점으로 겹쳐 돕니다.
  - 모션: 시점이 다른 회전 자세가 섞이면 몸의 방향이 튑니다.
  - 타격: 클립마다 자기 시각에 `Collision_AttackEnd`를 보내고, Precision은 그때 충돌을 전부 지웁니다. 한 벌이 충돌을 만들면 다른 벌이 곧 지워 버리는 일이 되풀이됩니다.
- 이동 중에 쓰이는데 우리가 바꾸지 않은 클립(질주 등)이 있을 가능성도 남아 있습니다.
- 어느 쪽인지는 확인하지 못했습니다. 어느 쪽이든 "여러 이동 클립에 회전과 타격 주석을 구워 넣는" 지금 구조의 약점입니다.

결정(2026-11-12, 설계-현황 결정 50): 아래 방향으로 바꿨습니다. 생성기의 기본이 정지 자세(`--mode static`)가 됐고, 1B 모드에는 `out/cyclone_pose.hkx` 하나만 들어 있습니다. DLL 쪽 구현과 시험 방법은 `../02-skill-input/README.md`의 "회전과 타격을 DLL로 옮김"에 있습니다.

고칠 방향(당시의 제안):

- 회전을 클립에 굽지 않습니다. 클립은 무기를 뻗은 **정지 자세**만 담고, 몸을 돌리는 것은 DLL이 매 프레임 합니다. 섞이는 클립이 모두 같은 자세이므로 튈 것이 없고, 회전 속도를 공격 속도에 맞춰 바꿀 수 있게 됩니다.
- 타격을 클립 주석에 맡기지 않습니다. DLL이 일정 주기로 주변의 적을 타격합니다. PoE의 사이클론이 원래 "무기 충돌"이 아니라 "주변 범위를 공격 속도에 맞춰 타격"하는 스킬이고, 통합 설계서 6.7의 "타격 주기는 무기 공격 속도의 300%"와도 맞습니다.
