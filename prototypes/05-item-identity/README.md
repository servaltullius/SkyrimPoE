# 프로토타입 5: 아이템의 동일성과 저장 왕복

상태: 4차와 5차 시험(2026-11-13)에서 깨끗한 세이브로 23단계가 모두 돌았고, 묻는 것 9가지에 답을 얻음(아래 "시험 기록" 4차의 판정, 5차는 검수 뒤의 재확인). 4차는 CalamityAffixes의 플러그인(esp)과 모드 설정을 끈 상태였고 DLL만 로드돼 있었음. DLL까지 뺀 확인이 남음.

**6차 시험 전(2026-11-13)**: 남은 구멍이던 "바닥을 거친 아이템을 잇는 방법"을 견주는 단계를 넣어 빌드함. 게임 안에서는 아직 돌리지 않음. 무엇을 견주는지와 통과 기준은 아래 "바닥을 거친 아이템 잇기(6차 준비)"에 있음. MO2의 `[PoE Proto] 5 Item Identity`에 배치함(사용자가 게임을 끈 뒤. DLL 10:47, 빌드 산출물과 같은 파일임을 확인).

**6차 시험(2026-11-13)은 대부분 쓰지 못함**: 6차 준비에서 넣은 스레드 검사가 이벤트 대부분을 버렸음(아래 "시험 기록"의 6차). 건진 사실이 몇 있고, 그 가운데 둘(내려놓을 때 컨테이너 이벤트의 참조 칸이 바닥 참조의 폼 ID라는 것, 바닥 참조에 남긴 번호가 주울 때 그대로 따라온다는 것)은 끼어들지 않고 잇는 길을 가리킴. 검사를 잠금으로 바꾼 7차의 빌드를 배치함(DLL 11:09).

**7차 시험(2026-11-13)에서 바닥 경로의 판정을 얻음**(아래 "시험 기록"의 7차). 줍기 일곱 번에서 틀린 답은 없었고, 끼어들지 않고 잇는 길(바닥 참조에 번호를 남기고, 주울 때 컨테이너 이벤트의 고유 ID 칸과 `참조:번호` 묶음으로 찾기)이 번호를 남긴 두 번 모두 맞았음. 줍기 함수에 끼어드는 길도 됨. 고유 ID만 가진 주괴는 묶음 없이 돌아와 표시를 잃음. 남은 것: 손으로 버리고 줍는 실제 조작, 주괴에 번호를 남긴 경우, 번호를 남긴 채 저장한 경우.

**8차 준비(2026-11-13)**: 위의 남은 것을 보는 단계를 넣어 빌드함(아래 "시험 기록"의 8차 준비). 자동 단계 뒤에 손으로 버리고 줍는 조작이 시험의 일부가 됨. MO2에 배치함(사용자가 게임을 끈 뒤. DLL 12:08, 빌드 산출물과 같은 파일임을 확인).

**8차 시험(2026-11-13)에서 남은 확인 넷에 답을 얻음**(아래 "시험 기록"의 8차): 주괴도 번호를 남기면 묶음으로 돌아옴, 남긴 번호는 저장을 거쳐도 남음, 손으로 버리고 줍는 실제 조작에서도 같은 길이 섬, 번호는 고유 ID 변경 이벤트 안에서 남겨도 됨(한 번). 번호를 남긴 줍기는 6·7·8차를 합쳐 열 번이고 모두 같은 모습이었음. 이 프로토타입이 바닥 경로에 대해 물은 것은 여기까지 답이 나옴.

**식별 수단이 확정됨(2026-11-13, 설계-현황 2장 59번)**: (가진 쪽의 폼 ID, 번호) 키를 고유 ID 변경 이벤트로 따라가고 코세이브에 저장하며, 바닥은 내려놓을 때 참조에 번호를 남기고 주울 때 컨테이너 이벤트의 고유 ID 칸과 `참조:번호` 묶음으로 이음. 줍기 함수 훅은 쓰지 않음. 설계는 통합 설계서 8.2, 남은 세부는 설계-현황 5장 38번.

**9차 준비(2026-11-13)**: 남은 경로(상인, 시체, 동료, 제작)를 보는 지켜보기 시험을 넣어 빌드하고 MO2에 배치함(DLL 12:32, INI는 `Scenario = watch`, `HookPickUp = false`). 사용자가 실제 메뉴로 아이템을 옮기고 플러그인은 확정된 방식대로 키를 따라가며 판정을 남김. CalamityAffixes의 DLL까지 뺀 환경은 이 결정에 필요하지 않아 공개 배포 전의 확인으로 미룸(설계-현황 5장 37번).

**9차 시험(2026-11-13)에서 실제 메뉴 경로의 판정을 얻음**(아래 "시험 기록"의 9차): 상인에게 팔았다 되사기, 동료에게 줬다 받기, 시체에서 꺼내기, 상자에 넣었다 꺼내기, 단련, 마법 부여, 메뉴에서 버리고 줍기를 사용자가 한 번씩 했고, 판정 23회에서 틀림과 끊김이 없었음. 옮기는 경로는 모두 고유 ID 변경 이벤트가 왔고, 단련과 마법 부여는 고유 ID를 바꾸지 않았음. 줍기 함수에 끼어들지 않는 절차가 손으로 주운 것을 실제로 이었음(한 번). 이 프로토타입이 아이템 쪽에 대해 물은 것은 여기까지 답이 나옴. 남은 것은 보지 않은 경우들(아래 9차의 "아직 보지 못한 것")과 설계로 정할 세부(설계-현황 5장 38번).

통합 설계서 14장의 12번("아이템과 젬의 동일성")과 11번("저장 왕복")에 해당합니다. 폴더 번호가 5인 것은 만든 순서입니다.

## 무엇을 확인하는가

감정한 장비에는 어픽스가 붙고, 그 장비가 나뉘고 합쳐지고 옮겨지고 팔리고 저장됐다 불려도 어픽스는 제 장비를 따라가야 합니다(통합 설계서 8.2, 13장). 그러려면 "이 아이템"을 다시 찾을 수단이 있어야 합니다. 설계서는 엔진의 고유 ID에 묶는다고 적었지만, 그 ID는 컨테이너를 옮길 때 바뀔 수 있다는 말이 있고(Grid Inventory의 헤더), 실행으로 확인한 것은 없습니다.

이 프로토타입의 첫 단계는 판단이 아니라 관찰입니다. 아이템에 붙일 수 있는 표시 세 가지가 각 경로에서 어떻게 되는지를 봅니다.

| 표시 | 내용 |
| --- | --- |
| 엔진의 고유 ID | `ExtraUniqueID`. 값 두 개의 쌍. 헤더의 필드 이름은 `baseID`와 `uniqueID`인데, 2차 시험에서 본 `baseID`는 아이템의 베이스가 아니라 **가진 쪽(플레이어, 상자)의 폼 ID**였고 `uniqueID`는 그 인벤토리 안에서의 번호였음 |
| 표시 이름 | `ExtraTextDisplayData`. 플레이어에게 보이는 이름 |
| 숨은 꼬리표 | `ExtraHealth`(단련 수치)에 아주 작은 값을 넣은 것. 이름이 바뀌는 문턱보다 작아 겉으로 보이지 않음. 이 시험에서는 고유 ID가 같은 두 아이템을 가려내는 기준으로 씀 |

묻는 것:

1. 표시한 아이템이 같은 베이스의 표시 없는 아이템과 섞이지 않는가(나누기, 합치기).
2. 플레이어에서 상자로, 다시 플레이어로 옮겼을 때 표시가 남는가. 고유 ID의 번호가 바뀌는가.
3. 바닥에 버렸다 주웠을 때 남는가.
4. 장착했다 풀었을 때 남는가.
5. 판매 이유로 다른 컨테이너에 넘겼다 되찾았을 때 남는가.
6. 저장하고 불러온 뒤에 남는가. 코세이브에 적어 둔 번호와 같은가.
7. 다른 세이브를 불러오면 이전 세이브에서 온 우리 쪽 상태가 비워지는가. 코세이브에 우리 기록이 없는 세이브에서는 어떻게 되는가.
8. 고유 ID가 같은 종류인 두 아이템(꼬리표 A, B)이 서로 바뀌지 않는가.
9. 컨테이너를 옮길 때 게임이 보내는 이벤트(`TESContainerChangedEvent`)에 무엇이 실려 오는가.

## 통과 기준

게임 안에서 재기 전에 정한 기준입니다. 이 단계에서는 "식별 수단으로 쓸 수 있는가"를 표시마다 판정합니다.

| 항목 | 쓸 수 있음 | 조건부 | 쓸 수 없음 |
| --- | --- | --- | --- |
| 섞이지 않음(1) | 표시한 것이 따로 남고 개수가 맞음 | | 표시 없는 것과 합쳐짐 |
| 옮기기·버리기·장착·판매(2~5) | 모든 경로에서 표시가 남고 값이 같음 | 표시는 남지만 값이 바뀜(바뀐 값을 그때 알 수 있어야 함) | 어느 경로에서든 표시가 사라짐 |
| 저장 왕복(6) | 불러온 뒤 표시가 남고 저장 때의 값과 같음 | 남지만 값이 바뀜 | 사라짐 |
| 서로 바뀌지 않음(8) | 두 아이템의 꼬리표와 고유 ID의 짝이 끝까지 유지됨 | | 짝이 바뀜 |
| 세이브 넘나들기(7) | 다른 세이브를 불러오면 우리 쪽 상태가 비워지고, 돌아오면 다시 맞음 | | 이전 세이브의 상태가 남음 |

"쓸 수 있음"인 표시가 하나도 없으면, 보존되는 경로의 목록과 보존하지 못했을 때의 복구 방침을 정하는 쪽으로 갑니다(설계서 8.2의 미정 항목).

## 플러그인이 하는 일

`plugin/`의 DLL(`PoEProtoItems.dll`)이 INI의 `StartKey`(기본 F10)를 누르면 아래를 스스로 차례로 돌리고, 단계마다 인벤토리의 상태를 `Documents\My Games\Skyrim Special Edition\SKSE\PoEProtoItems.log`에 남깁니다. 게임을 한 번 켜서 표 하나를 얻으려는 것입니다(약 1분에 불러오기 세 번의 시간. 5차까지는 약 40초였고 6번과 9~10번이 지금과 달랐습니다).

1. 기준 세이브를 저장합니다(`PoEProto5_baseline`).
2. 발밑에 빈 상자를 놓고, 철 검 5개, 철 투구 2개, 철 주괴 2개를 인벤토리에 넣습니다.
3. 표시를 붙입니다. 검 넷, 투구 하나, 주괴 하나를 바닥에 내려놓고, 그 참조에 꼬리표나 이름을 붙여 다시 주운 뒤, 고유 ID를 붙입니다.
   - 검: 고유 ID만 / 고유 ID + 꼬리표 A / 고유 ID + 꼬리표 B / 이름만 / 표시 없음
   - 투구와 주괴: 고유 ID만 / 표시 없음
4. 표시 없는 검을 하나 더 넣습니다(합치기).
5. 표시한 것을 모두 상자로 옮겼다가 다시 꺼냅니다.
6. 표시한 것 다섯(검 셋, 주괴, 투구)을 바닥에 내려놓고, 하나씩 줍습니다. 줍기마다 여러 방법의 답을 정답과 견줍니다(아래 "바닥을 거친 아이템 잇기").
7. 투구(고유 ID)를 장착했다 풉니다.
8. 검(꼬리표 B)을 판매 이유로 상자에 넘겼다 되찾습니다.
9. 검(이름)을 바닥에 내려놓은 채로 표시한 세이브를 저장합니다(`PoEProto5_marked`). 코세이브에 표시마다의 위치와 고유 ID를, 바닥에 있는 것은 그 참조의 폼 ID를 적습니다.
10. 표시한 세이브를 불러와 견주고 바닥의 검을 줍습니다. 기준 세이브를 불러와 견줍니다. 표시한 세이브를 다시 불러와 견주고 바닥의 검을 다른 길로 줍습니다.

로그의 줄은 다음과 같습니다.

- `[바닥]`: 내려놓거나 줍는 순간의 바닥 참조(폼 ID와 부가 데이터).
- `[잇기:이벤트 시점]`, `[잇기:줍기 뒤]`: 줍기 하나를 두 시점에서 본 것. 이벤트에 실린 참조, 바닥에 있던 참조들의 상태, 플레이어가 가진 묶음들.
- `[줍기 함수]`: 줍기 함수에 끼어들어 본 것(들어올 때의 참조, 나갈 때 새로 생긴 묶음).
- `[잇기]`: 잇는 절차가 실제로 한 일.
- `[잇기 판정]`: 방법마다의 답과 정답의 비교.

- `[상태:단계]`: 플레이어와 상자의 인벤토리에서 시험용 폼들의 개수와, 부가 데이터 묶음 하나하나의 내용.
- `[추적:단계]`: 표시한 아이템 여섯 개가 지금 어디에 어떤 고유 ID로 있는지. 단계 사이를 견주는 표가 됩니다. 표시가 사라졌으면 "찾지 못함"으로 나옵니다. 줄 끝에 판정이 둘 붙습니다. "키"는 아래의 따라간 키와, 그것이 찾은 아이템의 고유 ID와 맞는지(맞음, 어긋남)입니다. 이 판정은 꼬리표나 이름이 있는 표시에서만 뜻이 있습니다(내용으로 찾았으므로). 고유 ID만 붙인 표시는 키로 찾기 때문에 맞을 수밖에 없어 "키로 찾음"이라고만 나옵니다. "묶음"은 찾은 것이 표시를 붙일 때의 그 부가 데이터 묶음인지(같음, 다름, 대조 불가)이고, 키와 따로 하는 확인입니다. 바닥을 거치거나 불러오면 묶음이 새로 만들어지므로 그때는 "다름"이나 "대조 불가"가 정상입니다.
- `[이벤트] 컨테이너 변경`: 게임이 보낸 컨테이너 변경 이벤트(`TESContainerChangedEvent`)의 내용.
- `[이벤트] 고유ID 변경`: 게임이 아이템의 고유 ID를 바꿀 때 보내는 이벤트(`TESUniqueIDChangeEvent`)의 내용. 표시한 아이템의 것이면 "따라감"이 붙습니다.
- `[환경]`: 결과에 영향을 줄 수 있는 다른 모드의 상태(지금은 CalamityAffixes). DLL이 로드됐는지와 플러그인 파일(esp)이 켜져 있는지를 따로 적습니다. 그 모드가 제 설정에서 꺼져 있는지는 그 모드의 로그를 봐야 합니다.
- `[코세이브:…]`: 저장 때 적은 값과 불러온 뒤의 값의 비교.

표시한 아이템은 두 가지로 찾습니다. 꼬리표나 이름이 있는 것은 그 내용으로 찾습니다(이것이 정답입니다). 고유 ID만 있는 것은 **따라간 키**로 찾습니다. 키는 표시를 붙일 때의 고유 ID(가진 쪽, 번호)이고, 게임이 고유 ID 변경 이벤트를 보낼 때마다 새 값으로 옮깁니다. 저장할 때는 코세이브에 적고, 불러온 뒤에는 코세이브의 값으로 되살립니다. 본 모드가 어픽스를 아이템에 묶으려면 해야 할 일을 그대로 해 보는 것입니다. 꼬리표가 있는 아이템에서는 따라간 키가 정답과 맞는지도 함께 나옵니다.

고유 ID가 이미 붙어 있으면 그대로 두고, 없을 때만 `ExtraUniqueID`를 직접 만들어 붙입니다. 값은 2차 시험에서 본 모양을 따릅니다: 앞은 가진 쪽의 폼 ID, 뒤는 그 인벤토리에서 안 쓰인 번호(0x7001부터). 엔진의 `InventoryChanges::SetUniqueID`를 부르지 않는 이유는 아래 "시험 기록"의 1차에 있습니다. 그래서 이 시험은 "고유 ID가 붙은 아이템이 각 경로에서 어떻게 되는가"는 보여 주지만, "엔진이 번호를 어떻게 매기는가"는 보여 주지 않습니다.

표시를 붙일 때 바닥을 거치는 이유: 인벤토리 안의 아이템에 부가 데이터 묶음을 새로 만들어 붙이려면 묶음을 만드는 함수가 필요한데, 이 CommonLibSSE-NG에는 그 생성자가 선언만 있고 구현이 없습니다(SE와 AE에서 구조가 다름). 그래서 게임이 만든 묶음(바닥에 놓인 참조가 가진 것)을 씁니다. 본 모드에서 인벤토리 안의 아이템에 어떻게 표시를 붙일지는 이 결과를 보고 정합니다.

## 바닥을 거친 아이템 잇기(6차 준비)

4차 시험의 결론은 "변경 이벤트로 따라가면 되는데, 바닥에서 주울 때만 이벤트가 오지 않아 끊긴다"였습니다. 6차는 그 구멍을 메울 방법을 견줍니다.

### 먼저 읽은 것: CalamityAffixes의 방식

사용자의 CalamityAffixes(v2.3.2 뒤의 `f089573`, 2026-11-09)가 같은 문제를 다루고 있어 소스를 읽었습니다(`include/CalamityAffixes/InstanceKeyTransferPolicy.h`, `WorldItemTransitLedger.h`, `src/EventBridge.Loot.cpp`, `src/EventBridge.Events.cpp`). 읽어서 안 것이고, 그 동작을 여기서 실행으로 확인한 것은 아닙니다.

- 내려놓을 때: 고유 ID 변경 이벤트(플레이어의 번호 → 바닥의 참조, 번호 0)를 받아, 상태를 "그 참조의 폼 ID"에 묶인 키로 옮깁니다.
- 주울 때: 컨테이너 변경 이벤트에 실린 참조가 그 키의 참조와 정확히 같을 때만 상태를 되돌립니다. 참조는 이벤트를 받은 순간에 바로 읽어 둡니다(나중에 처리할 때는 참조가 사라져 있을 수 있어서).
- 돌아온 아이템이 인벤토리의 어느 묶음인지: 이벤트에 번호가 있으면 그 번호. 없으면 인벤토리에서 고릅니다. 고유 ID가 아직 그 참조를 가리키는 묶음이 하나면 그것, 그런 것이 없고 고유 ID가 없는 묶음이 하나뿐이면 그것, 그 밖에는 고르지 않습니다(`ChooseReturnedItem`). 고른 묶음에는 엔진 함수(`InventoryChanges::GetNextUniqueID`)로 새 번호를 매깁니다. 이벤트 시점에 아이템이 아직 인벤토리에 없을 수 있다고 보고 다음 작업에서 한 번 더 시도합니다.
- 스크립트가 내려놓고 다시 넣는 경우(주석의 예: Temper and Recharge Services): 컨테이너 이벤트에 참조가 실리지 않는다고 적혀 있습니다. 이때는 "30초 안에 바닥으로 나간 그 폼의 아이템이 하나뿐일 때만" 잇고, 둘 이상이면 잇지 않습니다(`WorldItemTransitLedger`).
- 줍기 함수에 끼어드는 코드는 없습니다.

우리 5차까지의 관찰과 맞춰 볼 점: 우리 시험은 내려놓기와 줍기를 플러그인이 직접 불렀고, 그때 컨테이너 이벤트의 참조는 모두 0이었습니다. CalamityAffixes의 주석대로라면 이것은 "스크립트 경로"의 모습이고, 플레이어가 메뉴에서 버리고 조준해서 줍는 경로에서는 참조가 실려 올 수 있습니다. 다만 우리 로그는 핸들에서 참조를 얻지 못했다는 것만 적었고 핸들의 값 자체는 적지 않았습니다. 6차부터 둘을 따로 적습니다.

### 견주는 것

줍기 하나에 두 가지를 답해야 합니다.

**어느 표시가 돌아왔는가**

| 방법 | 내용 | 끼어들기 |
| --- | --- | --- |
| 컨테이너 이벤트의 참조(핸들로 읽음) | 이벤트의 참조 칸을 핸들로 보고 얻은 참조가 따라가던 바닥 참조와 같은가 | 없음 |
| 컨테이너 이벤트의 참조 칸(폼 ID로 읽음) | 그 칸의 값 자체가 따라가던 바닥 참조의 폼 ID와 같은가(6차에서 내려놓을 때 그랬음. 7차부터 견줌) | 없음 |
| 컨테이너 이벤트의 고유 ID 칸(남긴 번호) | 이벤트의 고유 ID 칸이 바닥 참조에 남겨 둔 번호와 같은가(6차에서 한 번 그랬음. 7차부터 견줌) | 없음(바닥 참조의 데이터를 고침) |
| 사라진 참조 | 따라가던 바닥 참조 가운데 지금 사라진(찾을 수 없거나 삭제·꺼짐 표시가 붙은) 것이 하나뿐인가. 이벤트 시점과 줍기 뒤, 두 번 봄 | 없음 |
| 줍기 함수가 받은 참조 | 플레이어의 줍기 함수(`Actor::PickUpObject`)에 끼어들어, 주울 참조를 직접 봄 | 가상 함수 하나 |
| 고유 ID 변경 이벤트(번호 남기기) | 내려놓은 참조에 고유 ID(그 참조, 우리가 고른 번호)를 직접 남겨 두면, 주울 때 엔진이 변경 이벤트를 보내 주는가 | 없음(바닥 참조의 데이터를 고침) |

**인벤토리의 어느 묶음이 그것인가**

| 방법 | 내용 |
| --- | --- |
| 묶음 규칙 | CalamityAffixes의 `ChooseReturnedItem`을 옮긴 것. 이벤트 시점과 줍기 뒤, 두 번 봄. 번호를 남긴 아이템이 그 번호를 단 채 들어오면 이 규칙의 "참조를 가리키는 묶음"에 걸림 |
| 줍기 함수의 앞뒤 차이 | 줍기 함수를 부르기 전과 뒤의 묶음 목록을 견줘 새로 생긴 하나 |

**내려놓는 길과 줍는 길을 섞은 표** (내려놓는 순서. 줍는 순서는 검/고유ID → 꼬리표A → 주괴 → 투구 → 꼬리표B로, 내려놓은 순서와 다르고 번호를 남긴 둘이 끝)

| 표시 | 내려놓기 | 번호 남기기 | 줍기 |
| --- | --- | --- | --- |
| 검/고유ID+꼬리표A | `RemoveItem`(버리기 이유) | | `PickUpObject` 직접 호출 (5차까지와 같은 길) |
| 검/고유ID+꼬리표B | `Actor::DropObject` | 남김 | 활성화(`ActivateRef`) |
| 검/고유ID | `Actor::DropObject` | | 활성화 |
| 주괴/고유ID | `RemoveItem` | | `PickUpObject` |
| 투구/고유ID | `RemoveItem` | 남김 | `PickUpObject` |
| 검/이름 (저장할 때 바닥에 둠) | `Actor::DropObject` | | 불러온 뒤 활성화, 다시 불러온 뒤 `PickUpObject` |

철 검 셋이 함께 바닥에 있으므로 "그 폼의 아이템이 하나뿐일 때만" 같은 규칙은 답하지 못하게 됩니다.

정답은 시험이 알고 있습니다. 어느 표시를 주웠는지는 단계가 정했고, 어느 묶음인지는 줍기 전에는 없던 묶음입니다(한 번에 하나만 줍습니다). 꼬리표나 이름이 있는 표시는 내용으로 찾은 묶음과도 견줍니다.

**어느 판정이 따로 선 근거인가** (검수에서 나온 구분. 결과를 적을 때 지킬 것)

- 따로 선 근거: 꼬리표나 이름이 있는 표시의 "내용으로 찾은 묶음이 정답과 같음". 꼬리표A, 꼬리표B, 이름표 검 두 번, 모두 네 번입니다. 끼어들지 않는 방법들(이벤트의 참조, 사라진 참조, 묶음 규칙, 고유 ID 변경 이벤트)의 답도 정답과 다른 길로 나온 것입니다.
- 정의상 참에 가까운 것: "줍기 함수의 앞뒤 차이"는 정답과 같은 계산(줍기 전 목록과의 차이)을 시점만 달리한 것입니다. "줍기 함수가 받은 참조"는 `PickUpObject`를 직접 부른 줍기에서는 시험이 넘긴 참조를 되찾는 것입니다(활성화로 주운 세 번에서는 "활성화가 그 참조로 줍기 함수에 닿는다"는 것까지 보여 줍니다). 절차가 그 묶음의 고유 ID를 키로 삼았다면 "절차의 결과 맞음"도 같은 묶음과 견준 것입니다.
- 그래서 고유 ID만 붙인 표시(검, 투구, 주괴)의 줍기에서는 줍기 함수 쪽 판정이 "맞음"이어도 따로 선 확인이 없습니다. 로그에 그 줍기마다 "주의" 줄이 남습니다.

잇는 절차(키를 실제로 옮기는 일)는 본 모드가 하게 될 순서를 따릅니다. 줍기 함수에 끼어들 수 있으면 그것으로(참조와 앞뒤 차이), 줍기 함수를 거치지 않은 줍기는 이벤트의 참조(없으면 사라진 참조)와 묶음 규칙으로 잇습니다. 절차가 틀리면 판정 단계가 그 사실을 적고 정답으로 바로잡아, 뒤 단계(장착, 판매, 저장)가 이어지게 합니다. INI의 `HookPickUp = false`로 두면 끼어들지 않고 뒤쪽 절차만 돌립니다. 어느 설정이든 다른 방법들의 답은 로그에 함께 남습니다.

절차가 인벤토리를 고치는 것(돌아온 묶음에 고유 ID를 붙이거나 바꿔 쓰는 것)은 "줍기 뒤" 관찰이 끝난 다음에 합니다. 먼저 고치면 묶음 규칙이 우리가 고친 상태를 보게 되어, 끼어들지 않는 방법이 실제보다 나쁘게 나옵니다. "줍기 뒤"는 줍기 함수가 끝난 뒤에 맡긴 작업이 도는 시점이고, 시험이 직접 부른 줍기에서는 다음 프레임이 아니라 같은 프레임 안일 수 있습니다.

"절차의 결과"는 다섯 가지로 찍힙니다: 맞음 / 틀리게 이음 / 잇지 못함 / 견줄 수 없음(정답을 정하지 못함) / 잇지 못함(다시 묶을 묶음이 없음). 통과 기준에서 탈락은 "틀리게 이음"입니다.

**이 시험이 5차까지와 달라진 점**: 뒤 단계가 바닥 단계의 결과에 달려 있습니다. 묶음 없이 돌아오는 표시(주괴가 그럴 가능성이 있음)는 키가 비워져 저장 왕복에서 빠지고, 투구가 돌아오지 않으면 장착 단계가, 꼬리표B가 돌아오지 않으면 판매 단계가 건너뛰어집니다. 이름표 검은 바닥에 둔 채로만 저장 왕복을 봅니다(인벤토리 안에서의 저장 왕복은 4·5차에서 봤습니다). 자동으로 줍는 0.8~1.5초 사이에 같은 폼의 다른 줍기(자동 루팅 모드, 손 조작)가 끼면 답이 섞여 "정답을 정하지 못함"이 됩니다.

### 통과 기준 (게임 안에서 재기 전에 정함)

| 항목 | 쓸 수 있음 | 조건부 | 쓸 수 없음 |
| --- | --- | --- | --- |
| "어느 표시인가"의 방법 하나 | 일곱 번의 줍기에서 모두 맞음 | 답하지 못하는 경로가 있지만 틀린 답은 없음(어느 경로에서 되는지 적음) | 틀린 답이 한 번이라도 있음, 또는 한 번도 답하지 못함 |
| "어느 묶음인가"의 방법 하나 | 위와 같음 | 위와 같음 | 위와 같음 |
| 잇는 절차 전체 | 일곱 번 모두 "절차의 결과 맞음" | 묶음 없이 돌아오는 종류가 있고 그 밖에는 모두 맞음(그 종류를 적음) | 틀리게 이은 것이 있음 |
| 바닥에 둔 채 저장 | 불러온 뒤 참조가 같은 폼 ID로 있고 이름표가 그대로이며, 주운 뒤 내용으로 찾은 검의 고유 ID가 키와 맞음 | 참조는 있으나 폼 ID가 바뀜(바뀐 값을 알 수 있어야 함) | 참조나 이름표가 사라짐 |

끼어들지 않는 방법이 "쓸 수 있음"이면 그것을 권합니다(다른 모드와 부딪칠 자리가 없음). 줍기 함수에 끼어드는 방법만 "쓸 수 있음"이면 그 방법을 쓰되, 스크립트가 참조를 인벤토리에 넣는 경로처럼 줍기 함수를 거치지 않는 줍기는 따로 남습니다.

### 시험 뒤에 손으로 해 볼 것 (7차까지는 선택, 8차부터는 시험의 일부)

8차부터의 순서와 화면 안내는 아래 "시험 방법"에 있습니다. 이 항목은 6차 준비 때의 설명입니다.

"시험 끝" 알림 뒤에도 표시한 세이브에 머무는 동안에는 키가 살아 있어, 손으로 버리고 줍는 것이 같은 방식으로 기록됩니다. 플레이하던 세이브를 불러오기 전에 인벤토리에서 `PoE5 name tag` 검(또는 철 투구)을 메뉴로 버렸다가 조준해서 주우면, 실제 조작이 어느 길을 타는지(컨테이너 이벤트에 참조가 실리는지, 줍기 함수를 거치는지)가 로그에 남습니다. 주운 뒤에는 `[추적:손으로 주운 뒤]` 줄에서 이름표 검의 키가 "맞음"인지 봅니다.

### 실행으로 확인하지 않은 전제 (6차에서 새로 생긴 것)

- `Actor::DropObject`가 인벤토리 메뉴의 버리기와 같은 길이라는 것, `ActivateRef`가 조준해서 줍기와 같은 길이라는 것. 그럴 것으로 보고 골랐지만 확인하지 않았습니다. 그래서 표에는 함수 이름만 적었고, 실제 조작은 위의 "손으로 해 볼 것"으로 봅니다.
- `Actor::DropObject`의 가상 함수 자리(0xCB). 이 플러그인이 처음 부릅니다. 바로 다음 자리인 `PickUpObject`(0xCC)는 5차까지의 시험에서 실제로 아이템을 주웠고, 두 판(9.0.2, 12.1.0)의 헤더가 같은 순서로 적고 있습니다.
- `TESObjectREFR::ActivateRef`의 주소 번호(SE 19369, AE 19796). 두 판에서 같습니다. 같다는 것이 맞다는 증명은 아닙니다.
- 활성화가 곧바로 줍기로 이어진다는 것. 활성화가 거절되면(반환값 false) 판정 단계가 `PickUpObject`로 직접 줍고 그 줍기를 판정합니다. 활성화는 받아들여졌는데 1.5초 뒤에도 돌아오지 않았으면(다른 모드가 줍는 동작을 늦게 끝내는 경우일 수 있음) 다시 줍지 않고 그 표시를 바닥에 둔 채 넘어갑니다. 같은 참조를 두 번 줍지 않으려는 것입니다.
- `Actor::DropObject`가 내려놓은 참조를 돌려준다는 것. 돌려주지 않으면 고유 ID 변경 이벤트가 알려 준 참조로 이어 가고, 고유 ID가 없던 아이템이라 이벤트도 없으면 그 표시는 뒤 단계에서 빠집니다.
- 맡긴 작업이 맡긴 순서대로 돈다는 것("줍기 뒤" 관찰이 절차보다 먼저). 순서가 바뀌어도 절차가 관찰을 먼저 돌리게 해 두었습니다.
- 바닥의 참조에 고유 ID를 직접 남겨도 엔진이 받아들인다는 것. 주울 때 어떻게 되는지 모르는 것이 이 방법의 물음이라, 번호를 남긴 둘을 맨 끝에 줍습니다.
- 스레드: (6차에서 틀린 것으로 드러난 전제) "이벤트와 SKSE 작업이 한 스레드에서 돈다"고 보고 그 스레드의 이벤트만 썼다가 이벤트 대부분을 버렸습니다. 7차부터는 스레드를 따지지 않고 잠금으로 지키며, 못 잡아도 이벤트는 처리합니다. 남은 전제는 "이벤트는 그것을 일으킨 호출과 같은 스레드에서 온다"인데, 틀려도 시험은 돌고 `[잠금]` 줄로 드러납니다.
- 줍기 함수에 끼어든 자리를 이 모드팩의 다른 모드가 함께 쓰는지는 모릅니다. 끼어들기는 원래 함수를 그대로 부르므로 함께 동작할 것으로 봅니다.

## 시험 방법

아래는 자동 시험(INI의 `Scenario = auto`)의 순서입니다. 지금 배치된 INI는 `Scenario = watch`(지켜보기 시험)이고, 그 순서는 "시험 기록"의 "9차 준비"에 있습니다.

1. 플레이하던 세이브를 불러옵니다. 주변에 적이 없는 곳이 좋습니다(시험 도중 게임이 돕니다).
2. 메뉴를 모두 닫고 F10을 누릅니다. 화면 왼쪽 위에 시작 알림이 뜹니다.
3. 그대로 둡니다(약 1분). 아이템이 바닥에 떨어졌다 주워지고, 투구가 씌워졌다 벗겨지고, 저장과 불러오기가 세 번 일어납니다.
4. "자동 시험 끝" 알림이 뜨면, **세이브를 불러오지 말고** 인벤토리를 열어 `PoE5 name tag` 검을 버립니다. "버린 것을 기록했습니다"가 뜹니다.
5. 메뉴를 닫고 바닥의 그 검을 조준해서 줍습니다. "주운 것을 기록했습니다"가 뜨고 마무리 단계가 몇 초 돕니다(투구가 떨어졌다 주워짐). 조작하지 말고 둡니다.
6. "모두 끝났습니다"가 뜨면 **플레이하던 세이브를 다시 불러옵니다. 시험 뒤의 상태로 저장하지 마세요.**

4~5번은 8차부터 시험의 일부입니다(7차까지는 선택이었고 두 번 모두 기록이 없었습니다). 할 일을 잊었으면 F10을 다시 누르면 안내가 다시 뜹니다.

시험용 세이브(`PoEProto5_baseline`, `PoEProto5_marked`)에서는 시작하지 마세요. 이전 시험의 아이템이 인벤토리에 남아 있으면 플러그인이 알림을 띄우고 시작하지 않습니다. 5차까지의 시험이 남긴 시험용 세이브는 코세이브의 기록 형식이 달라(1판) 이 빌드가 읽지 않고 건너뜁니다.

시작 키로 F9를 쓰지 않는 이유: F9는 게임의 빠른 불러오기입니다. 첫 시험에서 F9를 누르자 빠른 불러오기와 시험이 함께 시작됐습니다. 다른 모드가 F10을 쓰고 있으면 INI의 `StartKey`를 바꿉니다.

시험이 남기는 것:

- 세이브 두 개: `PoEProto5_baseline`, `PoEProto5_marked`(와 각각의 `.skse` 파일). 플레이하던 세이브는 건드리지 않습니다. 시험이 끝나면 지워도 됩니다.
- 시험 세이브 안에만: 발밑의 빈 상자, 인벤토리의 철 검·철 투구·철 주괴.

INI의 `SaveLoad = false`로 두면 저장과 불러오기 없이 "플러그인이 하는 일"의 8번까지만 돌립니다. `HookPickUp = false`로 두면 줍기 함수에 끼어들지 않습니다.

## 실행으로 확인하지 않은 전제

- 바닥에 놓인 참조의 부가 데이터에 꼬리표를 붙이고 주우면, 인벤토리에서 따로 떨어진 묶음이 된다는 것. 안 되면 표시 단계에서 "찾지 못함"이 나오고 뒤 단계가 건너뛰어집니다.
- 직접 만들어 붙인 `ExtraUniqueID`를 엔진이 제가 붙인 것과 똑같이 다룬다는 것. 다르게 다루면 그 차이가 이 시험의 결과에 섞입니다.
- 직접 고른 번호(0x7001부터)가 엔진이 나중에 매기는 번호와 겹치지 않는다는 것. 엔진이 번호를 어디서 세는지는 확인하지 않았습니다.
- 플러그인에서 저장과 불러오기를 요청할 수 있다는 것(`BGSSaveLoadManager::Save`, `Load`). 불러오기가 180초 안에 끝났다는 알림이 오지 않으면 시험을 멈춥니다.
- 게임이 고유 ID를 바꿀 때마다 변경 이벤트를 빠짐없이 보낸다는 것. 빠지는 경로가 있으면 그 단계의 `[추적]`에서 고유 ID만 붙인 표시가 "찾지 못함"으로, 꼬리표가 있는 표시의 키가 "어긋남"으로 나옵니다.

## 시험 기록

### 1차 (2026-11-13): 시작하자마자 게임이 튕김

확인된 사실:

- F9를 누르자 게임의 빠른 불러오기가 먼저 돌았고(코세이브 되돌리기, 6초 뒤 불러오기 끝), 불러오기가 끝난 직후에 시험이 시작됐습니다. 키가 겹친 것은 사실입니다.
- 시험은 기준 세이브를 저장한 다음 단계(시험 준비)에서 죽었습니다. 크래시 로그의 주소 `PoEProtoItems.dll+0x19278`을 링커의 주소 표(`.map`)로 풀면 `Snapshot` 안이고, 플레이어의 인벤토리를 처음 읽는 자리입니다. 죽은 명령은 인벤토리 목록을 따라가다 엉뚱한 주소를 읽은 것입니다.
- 그 직전에 부른 것이 `RE::InventoryChanges::GetItemCount`입니다. 지금 쓰는 CommonLibSSE-NG 9.0.2는 이 함수의 AE 주소 번호를 16047로 적고 있고, 12.1.0은 16108로 적고 있습니다.
- 주소 라이브러리(1.6.1170)에서 16047은 `SkyrimSE.exe+0x225E20`, 바로 다음 번호 16048은 `+0x225E40`입니다. 크래시 로그의 레지스터에 남은 함수 주소가 `+0x225E40`이었습니다. 개수를 세는 함수가 아닌 다른 것이 불렸다는 뜻입니다.

결론: 튕긴 원인은 라이브러리에 잘못 적힌 주소 번호입니다. 엉뚱한 함수가 플레이어의 인벤토리 변경 데이터를 덮어썼고, 바로 뒤에 그 목록을 읽다가 죽었습니다. F9가 겹친 것은 원인이 아닙니다. 빠른 불러오기는 시험이 시작되기 전에 끝났고, 죽은 자리는 불러오기와 상관없는 코드입니다. 덮어쓴 뒤에 저장된 세이브는 없습니다(기준 세이브는 그 전 단계에서 저장됨).

남은 가설: 없음. 다만 "16108이 맞는 번호"라는 것은 12.1.0에 그렇게 적혀 있다는 것뿐이고 실행으로 확인하지 않았습니다. 그래서 그 번호로 고쳐 부르지 않고 함수를 쓰지 않는 쪽으로 고쳤습니다.

고친 것:

- 개수는 엔진 함수 없이 셉니다(베이스 컨테이너에 든 수 + 인벤토리 변경분).
- 고유 ID는 직접 만들어 붙입니다. `InventoryChanges::SetUniqueID`도 두 판의 AE 번호가 다릅니다(9.0.2는 16149, 12.1.0은 16147. 9.0.2에서는 16149가 다른 함수에도 적혀 있음).
- 시작 키를 F10으로 옮겼습니다.
- 이 플러그인이 부르는 나머지 엔진 함수(`ExtraDataList::Add`, `ActorEquipManager::EquipObject`·`UnequipObject`, `BGSSaveLoadManager::Save`·`Load`, `TESObjectREFR::PlaceObjectAtMe` 등)의 번호는 두 판에서 같습니다. 같다는 것이 맞다는 증명은 아니므로, 다음 시험에서 단계마다 로그가 이어지는지로 확인합니다.
- 빌드 폴더에 주소 표(`PoEProtoItems.map`)를 남깁니다. 크래시 로그의 "DLL+주소"를 함수 이름으로 풀 때 씁니다.

라이브러리의 번호 차이 전체는 `docs/설계-현황.md` 4.6에 적었습니다.

### 2차 (2026-11-13): 16단계까지 관찰, 불러오기에서 멈춤

튕기지 않았습니다. 23단계 가운데 17단계(표시한 세이브 저장)까지 돌았고, 18단계(불러오기)에서 3분 동안 멈췄다가 시험이 끊겼습니다. 같은 프로필에 CalamityAffixes(아이템에 어픽스를 붙이는 모드)가 켜져 있었습니다.

**시험 도구의 결함 (고침)**

- 단계가 시작된 시각이 18번 모두 밀리초까지 예정 시각과 같습니다(전부 `.288`). 프레임마다 돌았다면 0~16ms씩 어긋나야 합니다. 시험 전체가 한 프레임 안에서 돌았다는 뜻입니다.
- 원인은 진행 방식입니다. SKSE에 맡긴 작업이 끝날 때 스스로 다음 작업을 맡겼는데, SKSE가 맡겨진 작업이 없어질 때까지 한자리에서 돌리는 것으로 보입니다(위의 시각에서 나온 추론이고 SKSE 소스로 대조하지는 않았습니다). F10을 누른 뒤 3분 23초 동안 게임이 멈춰 있었을 것입니다.
- 불러오기는 요청만 되고 시작되지 못했습니다. 제한 시간(180초)이 지나 시험이 손을 놓자 0.24초 뒤에 불러오기가 시작돼 6초 만에 끝났습니다.
- 고친 것: 진행을 깨우는 일을 별도 스레드가 50ms마다 작업 하나를 맡기는 방식으로 바꿨습니다. 불러오기를 기다리는 동안에는 아무것도 맡기지 않습니다.
- 이 결함의 뜻: 아래 관찰은 모두 **프레임이 한 번도 지나지 않은 상태**에서 본 것입니다. 다음 프레임에 일어나는 일(다른 모드의 뒤처리, 바닥에 놓인 아이템의 물리와 3D)은 섞이지 않았습니다. 3차에서 다시 봐야 합니다.
- 08:32에 남은 크래시 로그는 다른 프로젝트의 시험용 도구 `CrashTester.dll`에서 난 것이고 이 플러그인은 호출 스택에 없습니다.

**관찰한 것** (로그의 사실)

| 경로 | 꼬리표(단련 수치) | 표시 이름 | 고유 ID |
| --- | --- | --- | --- |
| 플레이어 → 상자 → 플레이어 | 남음 | 남음 | 옮길 때마다 바뀜. `00000014:0018` → `FF0036E8:0002` → `00000014:0018` |
| 바닥에 버림 → 주움 | 남음 | 남음 | 버리면 없어짐(바닥의 참조에 고유 ID가 없음). 주우면 새로 받음 |
| 장착 → 해제 | 남음 | 남음 | 그대로 |
| 판매 이유로 상자에 → 되찾음 | 남음 | 남음 | 바뀜. `00000014:0019` → `FF0036E8:0001` → `00000014:0018` (떠날 때와 다른 번호로 돌아옴) |

- 고유 ID의 앞 값은 가진 쪽의 폼 ID입니다(플레이어 `00000014`, 상자 `FF0036E8`). 아이템의 베이스 ID가 아닙니다.
- 뒤의 번호는 받는 쪽 인벤토리에서 비어 있는 번호입니다. 상자에서는 1부터 차례로 받았고, 플레이어에게 돌아올 때는 그때 비어 있던 번호를 받았습니다. 꼬리표 B의 검은 0019로 떠나 0018로 돌아왔는데, 0018은 그 전에 꼬리표 A의 검이 쓰던 번호입니다. **번호만 기억해서는 다른 아이템을 가리키게 됩니다.**
- 컨테이너 변경 이벤트의 고유 ID 칸에는 받는 쪽에서의 새 번호가 들어 있습니다(컨테이너 사이를 옮길 때). 플레이어에게 새로 넣거나 주울 때는 0이었습니다.
- 같은 시각의 CalamityAffixes 로그에는 게임이 보낸 고유 ID 변경 이벤트가 옛 값과 새 값의 짝으로 남아 있습니다(예: 가진 쪽 `00000014` → `FF0036E8`, 번호 23 → 1. 바닥에 버릴 때는 새 번호가 0). 게임이 번호를 바꿀 때 알려 준다는 뜻입니다. 이 플러그인은 그 이벤트를 받지 않고 있었고, 3차부터 받습니다.
- 꼬리표가 붙은 묶음은 표시 없는 검과 합쳐지지 않았습니다. 다만 이 환경에서는 표시 없는 검과 투구도 넣자마자 하나씩 따로 묶음과 고유 ID를 받았습니다(검 5개를 한 번에 넣었는데 이벤트는 1개씩 다섯 번, 그중 넷이 고유 ID를 받음. 주괴는 받지 않음).
- 단련 수치 꼬리표가 붙은 검에는 표시 이름 데이터가 따라 붙었습니다(처음에는 빈 이름, 상자를 다녀온 뒤에는 '철 검').
- 컨테이너 사이를 옮길 때는 같은 묶음 객체가 그대로 옮겨 갔고, 버렸다 주우면 새 묶음이 됐습니다.

- **플레이어의 번호는 표시한 아이템끼리도 서로 바뀝니다.** `PoE5 B` 검은 `0018`로 나갔다가 `001D`로 돌아왔고, 투구는 `001D`로 나갔다가 `0018`로 돌아왔습니다. 값을 그대로 기억했다면 검의 키가 투구를 가리켰을 것입니다. 변경 이벤트로 따라간 키는 둘 다 맞았습니다. 돌아올 때의 번호 셋(`0017`, `0018`, `001D`)은 "비어 있는 가장 낮은 번호"와 어긋나지 않지만, 다른 번호가 쓰이고 있었는지를 보지 않아 규칙은 미확인입니다.
- **가진 쪽을 찾을 수 없던 동안.** 스키버를 가리키는 키(`FF000BCE:0001`)는 13:20:47의 판정에서는 찾았고, 13:21:44부터 13:22:31까지의 판정 아홉 번에서는 그 참조를 폼 ID로 찾을 수 없었습니다. 13:31:48에 그 스키버에서 아이템이 나오며 변경 이벤트가 왔고 키가 맞게 옮겨졌습니다. 즉 찾을 수 없던 동안에도 키는 옳았습니다. 그 사이 사용자는 상인과 거래하고 동료와 주고받았습니다. 스키버가 있던 셀이 메모리에서 내려간 것으로 보지만(추정), 사용자가 어디에 있었는지는 로그에 없습니다.
- **컨테이너 메뉴를 거치지 않은 꺼내기 둘.** 스키버와 상자에서 꺼낼 때 `ContainerMenu`가 열리지 않았고 이벤트는 작업 스레드에서 왔습니다. 이 프로필에 QuickLoot IE가 켜져 있어(`modlist.txt`) 그 화면으로 꺼낸 것으로 봅니다(추정). 이벤트의 모양은 메뉴를 거친 것과 같았습니다.
- 메뉴를 거친 이동의 이벤트는 모두 코세이브 콜백과 같은 스레드에서 왔습니다.
- 스키버에서 돌아온 `PoE5 B`의 묶음은 주소가 달라졌고(`@55940` → `@AB7C0`), 상인·동료·상자를 오간 묶음은 주소가 그대로였습니다. 묶음의 주소는 어느 쪽이든 키로 쓰지 않습니다.
- 13:59에 제작 메뉴가 0.1초 만에 닫힌 것이 두 번 있습니다. 무엇이었는지는 로그에 없습니다.

**아직 보지 못한 것**

- 표시한 아이템이 제작 재료로 쓰여 없어지는 경우, 마법 해제(아이템이 없어짐), 방어구 작업대.
- 상인의 상자가 초기화된 뒤(판 아이템이 사라짐), 동료가 받은 것을 장착하거나 동료가 죽거나 떠난 경우.
- 아이템이 상인·동료·시체에 있는 채로 저장하고 불러오는 것(지켜보기 시험은 저장하지 않음). 가진 쪽이 경량 플러그인의 참조(`FE…`)이거나 실행 중에 만들어진 참조(`FF…`)일 때 코세이브의 폼 ID가 풀리는지.
- 모두 가져가기, 한 번에 여러 개, 소매치기(되넣기), 감옥의 압수와 반환.
- 8차의 "아직 보지 못한 것" 가운데 NPC가 주운 경우, 바닥에서 주워지지 않고 사라진 경우, CalamityAffixes의 DLL까지 뺀 환경.
- `RemoveItem`으로 바닥에 내려놓는 경로에서 번호를 이벤트 안에 남기는 것.

**시험 도구에 남은 것**: 스키버를 죽이는 방법이 동작하지 않았습니다. 지켜보기 시험을 다시 돌린다면 고쳐야 합니다(지금은 고치지 않음).
